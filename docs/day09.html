一、SLAM 到底在解什麼問題

1-1 為什麼會有 SLAM 這個東西

機器人要導航，需要兩樣東西：一張地圖（環境長什麼樣）和自己在地圖裡的位置（pose）。問題是：

  • 如果你已經有地圖，要算出自己在哪 → 這叫 Localization（定位），是可解的（Day 10 的 AMCL）。
  • 如果你已經知道自己每一刻在哪，要畫地圖 → 這叫 Mapping（建圖），也是可解的（今天的 Occupancy Grid）。
  • 但真實情況是：兩個都不知道。要靠不準的輪速計（odometry）和有雜訊的雷射，同時把兩件事一起估出來。這就是 SLAM（Simultaneous Localization and Mapping），也是為什麼它被稱作「雞生蛋、蛋生雞」問題。
比喻：你被蒙眼帶到一棟陌生的大樓，只給你一根導盲杖（雷射）和一個會慢慢走鐘的計步器（odometry）。你要一邊走一邊在腦中畫平面圖，同時還要記住自己現在畫到圖上的哪一點。走久了計步器會漂，你腦中的位置就會偏，畫出來的牆就會歪；但如果你摸到一面「欸這面牆我剛剛摸過」的牆，你就可以回頭把整張圖修正——那個「欸我來過」的瞬間，就是 loop closure。

1-2 數學上的寫法（知道在算什麼就好）

p( x1:t , m | z1:t , u1:t )
  • x1:t：機器人從時刻 1 到 t 的所有 pose（位置 + 朝向）。這是我們想知道的「我在哪」。
  • m：地圖（map）。這是我們想知道的「環境長怎樣」。
  • z1:t：所有的觀測（observation），也就是每一幀 /scan 的雷射距離值。這是「我看到什麼」。
  • u1:t：所有的控制輸入（control），也就是「我叫輪子轉多少」，實務上就是 odometry 的增量。這是「我以為我移動了多少」。
  • p( · | · )：條件機率。整條式子念作「在我看到這些、我下了這些指令的前提下，我的軌跡和地圖長這樣的機率有多大」。SLAM 就是去找讓這個機率最大的那組 (軌跡, 地圖)。

要記住的重點只有一句：SLAM 的輸出不是一個確定答案，而是一個機率分布。所以地圖上的每一格不是「有牆／沒牆」，而是「有牆的機率是 0.83」。這直接解釋了為什麼建出來的圖有灰色。

學生常見誤解：「SLAM 就是把雷射點畫出來而已」。不是。單純把點畫出來叫 point cloud accumulation，走十公尺就會因為 odometry 漂移而糊成一團。SLAM 的核心價值是用觀測反過來修正位置估計（scan matching + loop closure），這才是它跟「畫點」的本質差別。

二、Occupancy Grid：地圖是怎麼存的

2-1 它解決什麼問題

電腦沒辦法存「一面牆」這種概念，只能存數字。Occupancy Grid（佔據柵格）的做法是：把地面切成一格一格的方格（TurtleBot3 預設 resolution = 0.05，也就是每格 5 公分），每格存一個數字代表「這格被東西佔住的機率」。

比喻：像遊戲裡的「戰爭迷霧」。整張圖一開始是未知的灰色，機器人走過、雷射掃過的地方才會被「點亮」成黑（有障礙）或白（空曠）。沒掃到的永遠是灰的。

2-2 ROS2 裡的實際數值

Topic 是 /map，型別是 nav_msgs/msg/OccupancyGrid。裡面的 data 是一個一維陣列（int8），值的定義是：

值意義rviz2 顯示存成 .pgm 時
0free，確定沒東西白色（淺灰）254（白）
100occupied，確定有障礙黑色0（黑）
-1unknown，沒掃到過灰色205（中灰）
1~99中間機率（不確定）深淺不一的灰依 thresholds 二值化

陣列是一維的，要自己換算成二維座標。公式：

index = y × width + x

而格子座標 (x, y) 換回世界座標（公尺）：

world_x = origin.x + (x + 0.5) × resolution
  • origin：地圖左下角在 map frame 裡的座標，存在 info.origin（也存在 .yaml 的 origin: 欄位）。它幾乎一定是負數，因為機器人啟動點通常被當成 (0,0)，而地圖往四面八方長。
  • resolution：每格幾公尺，0.05 就是 5 公分。
  • +0.5：取格子中心而不是左下角。忘了加這個會有半格（2.5 公分）的系統性偏移。
學生常見誤解：以為 data[0] 是地圖左上角。不是，是左下角（ROS 用右手座標系，y 向上）。用 OpenCV/matplotlib 畫出來上下顛倒，九成是這個原因，解法是 np.flipud()。

三、log-odds：為什麼要用「機率的對數」

3-1 它解決什麼問題

雷射每掃一次，都要更新格子的機率。如果直接存機率 p 並用 Bayes 公式更新，每次都要做乘法和除法（分母還要正規化），而且機率會被壓在 0 和 1 附近，浮點數精度會爛掉——一格被掃了 500 次都說「有牆」，機率會變成 0.99999999，再更新下去就數值失真了。

解法：改存 log-odds（對數勝算比）。

l = log( p / (1 − p) )
  • p：這格被佔據的機率。
  • p / (1−p)：odds（勝算比）。p=0.5 時 odds=1；p 越大 odds 越大。
  • l：取對數之後。p=0.5 → l=0（完全不知道）；p>0.5 → l 為正（傾向有障礙）；p<0.5 → l 為負（傾向空的）。範圍是 −∞ 到 +∞，不會被壓在邊界。

神奇之處在於，用了 log-odds 之後，Bayes 更新從「乘除」變成「加減」：

lt = lt−1 + lsensor − l0
  • lt−1：這格之前累積的信念。
  • lsensor：這一幀雷射對這格的「投票」。雷射打到的那格 → 加一個正值（inverse sensor model，例如 +0.85）；雷射光線穿過的那些格 → 加一個負值（例如 −0.4，因為光穿過代表那裡是空的）。
  • l0：先驗（prior）。通常設 0（代表一開始 p=0.5，什麼都不知道），所以實務上這項直接消失。
比喻：像法庭上的證據累積。每個證人（每一幀雷射）都投一票，說「我覺得有」或「我覺得沒有」，票數直接相加。看到很多次就票數很高，中間偶爾有一票反對也不會立刻翻盤——這正是為什麼 SLAM 對單幀雜訊有抵抗力，也是為什麼一個走來走去的人不會在地圖上留下實心黑塊（他離開後，後續穿過的光線會一直投負票，慢慢把他洗掉）。

要顯示地圖時再轉回機率：

p = 1 − 1 / (1 + el)
調參直覺：slam_toolbox 對應的參數是 occupancy_threshold（多高的機率才算黑）。設太低 → 一點雜訊就變黑牆，地圖髒；設太高 → 真的牆變成灰的，Nav2 的 costmap 會以為那裡可以走，直接撞牆。預設 0.1 對室內夠用。

3-2 光線穿過哪些格子？—— Bresenham

「雷射從機器人打到牆」是一條線段，要知道這條線經過哪些格子（好給它們投負票），用的是 Bresenham 直線演算法——就是電腦繪圖畫斜線的那個經典演算法，純整數加減、不用浮點除法，所以極快。這個叫 ray casting。知道這個名詞就好，不用會寫。

四、Bayes 濾波與粒子濾波（位置怎麼估）

4-1 Bayes 濾波：所有定位演算法的骨架

不管是 EKF、粒子濾波還是圖優化，骨架都是同一個兩步循環：

  1. Predict（預測 / motion update）：根據輪速計，把「我在哪」的機率分布往前推。因為輪速計不準，這一步一定會讓不確定性變大（分布變胖）。
  2. Update（更新 / measurement update）：拿雷射觀測跟已知地圖比對，把不符合觀測的可能性壓掉。這一步讓不確定性變小（分布變瘦）。
比喻：閉著眼睛走路。每走一步，你對自己位置的把握就變差一點（predict）；每張開眼睛看一次，把握就回來一些（update）。SLAM 就是這兩件事以 10~40 Hz 的頻率不停交替。
學生常見誤解：「odometry 不準，那乾脆不要用」。錯。predict 步驟需要 odometry 提供「移動的初始猜測」，scan matching 才有起點可以優化。完全沒有 odometry，scan matching 會找不到收斂方向。odometry 的角色是「大概對」，雷射的角色是「修正到精準」。

4-2 粒子濾波（Particle Filter）

問題：機率分布長什麼形狀？如果假設它是高斯分布（一個橢圓），就是 EKF——但真實的分布常常是多峰的（「我可能在走廊 A，也可能在長得一模一樣的走廊 B」），高斯表達不出來。

粒子濾波的做法很暴力也很聰明：用一大堆假設點（粒子）來近似任意形狀的分布。每個粒子是一個完整的猜測「機器人在 (x, y, θ)」。流程：

  1. 撒 N 個粒子（例如 2000 個），一開始隨機散布。
  2. Predict：每個粒子都照 odometry 移動，再各自加一點隨機雜訊。
  3. Weight：對每個粒子問「如果我真的在這，雷射應該看到什麼？」跟實際 /scan 比對，越像的權重越高。
  4. Resample：照權重重新抽樣——高權重的粒子被複製多份，低權重的被淘汰。粒子群自然就會聚集到正確位置。
比喻：派 2000 個偵察兵各自猜「我們在地圖的哪裡」，然後問每個人「照你的猜法，你左邊三公尺應該有牆，對嗎？」猜錯的被淘汰，猜對的多複製幾個。幾輪之後大家會擠在同一個地方——那就是答案。
助教必知：Nav2 的 AMCL 就是粒子濾波（Adaptive Monte Carlo Localization），Day 10 會用到。但 slam_toolbox 不是粒子濾波，它是 graph-based SLAM（見下一節）。舊的 gmapping 才是粒子濾波（Rao-Blackwellized PF）。學生問「slam_toolbox 是不是 gmapping 的新版」時，答案是：解決同一個問題，但用完全不同的方法。

4-3 為什麼 ROS2 主推 slam_toolbox 而不是 gmapping

gmapping（粒子濾波）slam_toolbox（圖優化）
核心方法每個粒子帶一整張地圖維護 pose graph，最後統一優化
記憶體大（N 張地圖）小（只存 node + 約束）
大場域會爆可以
Loop closure靠重採樣，弱明確偵測 + 全域優化，強
可否續建 / 編輯地圖不行可以（serialization、localization mode）
ROS2 支援已無官方維護官方主推

五、Loop Closure：SLAM 最關鍵的一步

5-1 它解決什麼問題

不管 scan matching 多準，每一幀都會有一點點誤差，而誤差會累積。繞著一棟建築走一圈回到原點，你估計的位置可能已經偏了兩公尺——地圖上就會出現「同一條走廊畫成兩條」的鬼影。

Loop closure 就是認出「我回到來過的地方了」，然後加一條「這兩個時刻的 pose 應該是同一點」的硬約束，再把整條軌跡拉回來。

比喻：像把一條有點鬆的項鍊，兩端扣起來的瞬間——整條鍊子會被拉緊，之前每一顆珠子的位置都會被微調。這就是 loop closure 觸發時，rviz2 裡整張地圖「啪」地跳一下、瞬間變整齊的原因。第一次看到會以為是 bug，其實那是 SLAM 最漂亮的時刻。

5-2 Pose Graph 是什麼

  • Node（節點）：某個時刻的機器人 pose，以及那時候的一幀 scan。
  • Edge（邊 / 約束）：兩個 node 之間的相對位移。有兩種來源：
    • Odometry edge：相鄰時刻之間，來自輪速計 + scan matching。
    • Loop closure edge：時間上相隔很遠、但空間上其實在同一處的兩個 node。
  • 優化（Ceres solver）：找一組 pose，讓「所有邊的實際差距」跟「邊上寫的約束」總誤差最小。這叫 graph optimization / bundle adjustment。
失敗模式：false loop closure。如果環境裡有兩個長得一模一樣的區域（例如兩條相同的走廊、一整排相同的隔間），SLAM 可能誤判「我回到原點了」，然後把兩個不同的地方硬扣在一起——地圖會瞬間扭曲成沒法用的樣子，而且不可逆。這是實驗室環境（一堆相同的桌腳）最常炸掉的原因。對應參數：loop_match_minimum_response_fine（調高＝更嚴格，寧可漏掉也不要誤判）。

6-3 建圖的開車技巧（這段決定地圖品質）

四條規則，講給學生聽：
  1. 慢。線速度壓在 0.15 m/s 以下，角速度 0.5 rad/s 以下。快 = scan matching 來不及收斂 = 牆變重影。
  2. 不要原地快速旋轉。純旋轉時 scan matching 的觀測幾何最差，是漂移最嚴重的動作。要轉就慢慢轉，或走弧線。
  3. 沿著牆邊走。雷射要看得到特徵。在空曠大廳中央繞圈，四周都是空的，scan matching 沒東西可以對，會直接漂掉。
  4. 刻意繞回起點。走一個封閉迴圈，讓 loop closure 有機會觸發。這是把地圖從「還行」變成「精準」的關鍵動作。

6-4 一邊建圖一邊觀察（開第五個終端機）

ros2 topic echo /map --field info --once
# 會看到 resolution / width / height / origin

# 看 tf 樹：map → odom → base_link → base_scan 有沒有完整接起來

# 產生 frames.pdf，用 evince frames.pdf 打開

# 直接查 map 到 base_link 的轉換（機器人現在在地圖哪裡）
ros2 run tf2_ros tf2_echo map base_link

# 看 slam_toolbox 有沒有在動（/map 更新頻率，正常約 0.5~2 Hz）
ros2 topic hz /map

ros2 topic echo /slam_toolbox/graph_visualization --field markers[0].points --once

6-5 存圖（兩種，都要會）

# ========== 方式 A：存成 .pgm + .yaml（Nav2 導航要用這個）==========
mkdir -p ~/maps && cd ~/maps
ros2 run nav2_map_server map_saver_cli -f my_map
# 產出兩個檔：my_map.pgm（圖片本體）、my_map.yaml（metadata）

# 加參數版本（門檻可調）
ros2 run nav2_map_server map_saver_cli -f my_map \
  --occ 0.65 --free 0.25 --ros-args -p use_sim_time:=true
# --occ：機率高於此值 → 存成黑（佔據）
# --free：機率低於此值 → 存成白（空曠）
# 兩者之間 → 存成灰（未知）

# ========== 方式 B：存成 slam_toolbox 專用序列化檔（可續建）==========
ros2 service call /slam_toolbox/serialize_map \
  slam_toolbox/srv/SerializePoseGraph "{filename: '/home/$USER/maps/my_map_serial'}"
# 產出 my_map_serial.posegraph + my_map_serial.data
# 這份保留了完整 pose graph，下次可以「接著建」或切成純定位模式。
# .pgm 是死的圖片，這份是活的。要補建圖一定要用這種。

6-6 打開存出來的檔案看看

cat ~/maps/my_map.yaml
image: my_map.pgm
mode: trinary
resolution: 0.05          # 每格 5 公分
origin: [-1.94, -2.72, 0] # 地圖左下角在 map frame 的 [x, y, yaw]，通常是負的
negate: 0                 # 0 = 白色代表 free（正常）；1 = 顏色反過來
occupied_thresh: 0.65     # 超過就算障礙
free_thresh: 0.25         # 低於就算空曠

用 Python 讀出來檢查（今天一定要跑一次這段，親眼看到數字）：

#!/usr/bin/env python3
# check_map.py —— 讀 .pgm + .yaml，印出統計並存一張預覽圖
# 需要：pip install numpy pyyaml pillow matplotlib
import numpy as np, yaml
from PIL import Image
import matplotlib.pyplot as plt

MAP = "/home/USERNAME/maps/my_map"   # ← 改成你的路徑（不含副檔名）

with open(MAP + ".yaml") as f:
    meta = yaml.safe_load(f)

img = np.array(Image.open(MAP + ".pgm"))
res = meta["resolution"]
ox, oy = meta["origin"][0], meta["origin"][1]

print(f"地圖尺寸（格）: {img.shape[1]} x {img.shape[0]}")
print(f"地圖尺寸（公尺）: {img.shape[1]*res:.2f} x {img.shape[0]*res:.2f}")
print(f"origin（左下角世界座標）: ({ox:.2f}, {oy:.2f})")

# .pgm 的慣例：0=黑=障礙, 205=灰=未知, 254=白=空曠
occ  = int((img < 60).sum())
unk  = int(((img >= 60) & (img < 240)).sum())
free = int((img >= 240).sum())
tot  = img.size
print(f"障礙 {occ:7d} ({occ/tot:5.1%})")
print(f"未知 {unk:7d} ({unk/tot:5.1%})   ← 這個比例太高代表沒探索完")
print(f"空曠 {free:7d} ({free/tot:5.1%})")

# 驗證座標換算：把地圖正中央那格換算成世界座標
cx, cy = img.shape[1]//2, img.shape[0]//2
# 注意：.pgm 是「上」為第 0 列，OccupancyGrid 是「下」為第 0 列，所以 y 要翻
wy = oy + (img.shape[0] - 1 - cy + 0.5) * res
wx = ox + (cx + 0.5) * res
print(f"影像中心格 ({cx},{cy}) → 世界座標 ({wx:.2f}, {wy:.2f}) 公尺")

plt.imshow(img, cmap="gray", vmin=0, vmax=255)
plt.title("my_map.pgm"); plt.colorbar()
plt.savefig("map_preview.png", dpi=120)
print("已存 map_preview.png")

九、🎓 助教筆記：學生最會卡的 5 個地方

卡點 1：rviz2 裡什麼地圖都沒有，一片空白

症狀：跑起來了但 rviz2 全灰／全空，/map 有 topic 但沒資料。
最可能原因（八成是這個）：忘了 use_sim_time:=true。
錯誤訊息（在 slam_toolbox 那個終端機）： 
[slam_toolbox]: Message Filter dropping message:
  frame 'base_scan' at time 1234.567 for reason 'discarding message because
  the queue is full'
或
Lookup would require extrapolation into the past.
Requested time 1234.5 but the earliest data is at time 1760000000.0
診斷指令： 
ros2 param get /slam_toolbox use_sim_time     # 必須是 true
ros2 topic hz /clock                          # Gazebo 有在發時間嗎
ros2 topic hz /scan                           # 雷射有在發嗎（應該約 5~10 Hz）
解法：關掉 slam_toolbox，重新加上 use_sim_time:=true。另外 rviz2 也要設：左側 Global Options → 或啟動時加 --ros-args -p use_sim_time:=true。
次要原因：rviz2 的 Fixed Frame 還停在 base_link 或 odom，要改成 map。

卡點 2：地圖有了，但牆是「雙重影」／整個歪掉

症狀：同一面牆畫成兩條平行線，或走廊變成扇形展開。
原因：odometry 漂移 + scan matching 沒跟上，通常是開太快或原地猛轉。
診斷： 
# 看 map → odom 的修正量。這個值代表「SLAM 認為 odometry 錯了多少」
ros2 run tf2_ros tf2_echo map odom
# 正常應該在幾公分內慢慢變。如果一下跳到 0.5 m 以上，就是漂了。
解法：
1. 重來一次，速度壓到 0.1 m/s、角速度 0.3 rad/s。
2. 調 minimum_travel_heading 從 0.5 降到 0.2（轉彎時多取樣）。
3. 走封閉迴圈讓 loop closure 修正。
要跟學生強調：這不是 bug，這就是 SLAM 的本質限制。學會「開車配合演算法」是實機部署的核心技能，不是靠調參就能完全解決的。

卡點 3：map_saver_cli 卡住不動，最後 timeout

錯誤訊息： 
[map_saver]: Timed out waiting for map subscription
[ERROR] [map_saver_cli]: Failed to save the map
三個可能原因，按順序檢查： 
# 1. slam_toolbox 還在跑嗎？（存圖時不能關掉它）
ros2 node list | grep slam

# 2. /map 真的有資料嗎？
ros2 topic echo /map --field info --once

# 3. use_sim_time 不一致（map_saver 用牆鐘、slam 用模擬時間）
ros2 run nav2_map_server map_saver_cli -f my_map --ros-args -p use_sim_time:=true
還有一個很坑的：ROS_DOMAIN_ID 在不同終端機設得不一樣，兩邊根本看不到彼此。用 echo $ROS_DOMAIN_ID 在每個終端機都確認一次。

卡點 4：存出來的 .pgm 用小畫家打開是「上下顛倒」的

症狀：學生說「地圖存錯了，跟 rviz2 裡看到的不一樣」。
真相：沒存錯。OccupancyGrid 的第 0 列是地圖最下面（ROS 右手座標系，y 向上）；而 .pgm／一般影像格式的第 0 列是最上面。map_saver 存檔時已經翻過一次了，所以用看圖軟體開會跟 rviz2 一致；但如果學生自己用 Python 直接讀 /map 的 data 陣列去 imshow，就會上下顛倒。
解法：np.flipud(grid)。
講給學生的一句話：「ROS 的 y 往上，圖片的 row 往下，兩個永遠差一個翻轉。這個坑之後在 costmap、在相機影像對應點雲時還會再遇到好幾次。」

卡點 5：地圖上有一條「幽靈軌跡」（人或動態物體的殘影）

症狀：地圖上有一條斷斷續續的黑點軌跡，那是實驗時走過的人。
原因：Occupancy Grid 假設環境是靜態的。動態物體被雷射打到就會投「有障礙」的正票。
為什麼有時會自己消失：人走掉之後，後續穿過那裡的雷射光線會一直投負票（log-odds 減），累積夠多次就洗白了。但如果那個人只出現在你剛好經過一次的地方，就永遠留在圖上。
解法：
1. 建圖時清場，別讓人在雷射高度（TurtleBot3 約 20 cm）走動。
2. 事後直接用 GIMP／小畫家把 .pgm 的黑點塗成白色（254）——這是完全合法的做法，實務上大家都在修圖，記得跟學生講，不然他們會覺得作弊。
3. 順便把玻璃門的位置手動塗成黑色（雷射穿透玻璃看不到，Day 25 會詳談）。
