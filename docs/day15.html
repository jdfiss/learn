知識點逐個講解

1. move_group：為什麼要有一個「大腦 node」

它解決什麼問題。要讓手臂從 A 移到 B，你至少需要：知道機器人現在在哪（joint states）、知道世界上有什麼障礙（碰撞物件）、算出目標姿態對應的關節角（IK）、找一條不撞到東西的關節空間路徑（motion planning）、把路徑加上速度與時間（trajectory）、送給控制器執行。如果每個功能各自寫一個 node，它們會各自維護一份不同步的世界狀態——這是災難。MoveIt2 的解法是把這些全部塞進一個叫 move_group 的 node，對外只開三種介面。

比喻。move_group 是餐廳的出餐口。你（使用者）不會跑進廚房自己炒菜，你只在出餐口點單：「我要手掌到桌上這個位置」。廚房裡誰切菜（IK）、誰查食材有沒有過期（碰撞檢查）、誰決定上菜順序（軌跡時間），你不管。壞處也一樣：出餐口一塞住，整間店都不出菜——這就是為什麼 MoveIt 的 debug 幾乎都在看 move_group 那個 terminal 的輸出。

三種介面（助教一定要記）：

介面形式用在哪
MoveGroupInterface（C++）函式呼叫（內部包 action client）正式專案、效能敏感
moveit_py / pymoveit2Python課堂教學、快速原型（明天 Day 16 主打）
/move_actionROS 2 Action跨語言、想自己組 goal message 時
學生常見誤解。「我寫的 Python 腳本自己在算 IK 跟規劃。」不是。你的腳本只是把 goal 包成 action goal 丟給 move_group，真正的計算全在 move_group 那個 process 裡。所以腳本印出 "planning failed" 時，錯誤細節不在你的 terminal，在 move_group 的 terminal。這一點沒講清楚，學生會花兩小時在自己的腳本裡加 print。

2. URDF vs SRDF：長相 vs 語意

它解決什麼問題。URDF（Day 6 學過）只描述物理事實：有哪些 link、質量多少、joint 在哪、極限多少、視覺與碰撞幾何長怎樣。但規劃器還需要知道一些 URDF 講不出來的事：「哪 7 個 joint 合起來叫做『手臂』？」「哪兩個 link 在物理上根本永遠不可能碰到，不用每次都檢查？」「『home 姿態』是指哪組角度？」這些是語意資訊，寫在 SRDF（Semantic Robot Description Format）。

URDFSRDF
回答的問題機器人是什麼機器人怎麼被使用
典型內容link / joint / inertial / visual / collision / meshgroup、group_state、end_effector、virtual_joint、disable_collisions
誰讀它robot_state_publisher、Gazebo、RViz、規劃器只有 MoveIt
改了會怎樣模型形狀/動力學變了規劃行為變了，但機器人外觀不變

disable_collisions 這一段值得特別講：MoveIt Setup Assistant 會隨機取樣上萬組姿態，統計出「從來沒碰過」「總是碰在一起（相鄰 link）」「預設姿態就碰在一起」的 link pair，把它們寫進 SRDF 停用檢查。一組 7 軸手臂大概有 C(n,2) 對 link 要檢查，停用掉七八成之後碰撞檢查才跑得動。

學生常見誤解。「我在 URDF 加了一個新的 link（例如夾具上的相機支架），為什麼 MoveIt 一直說 start state in collision？」因為新 link 沒有出現在 SRDF 的 disable_collisions 清單裡，它跟旁邊的 link 幾何重疊就被判定碰撞。改 URDF 之後要重跑 Setup Assistant 或手動補 SRDF——這是課堂上最常見的「明明只加了一塊板子卻整個壞掉」。

3. Planning Scene：MoveIt 心裡的那個世界

它解決什麼問題。規劃器要問「這個姿態會不會撞到」，就得有一份「世界現在長怎樣」的快照。Planning Scene 就是這份快照，由三部分組成：

  1. Robot State：所有 joint 的當前角度（從 /joint_states 來）。
  2. World：CollisionObject（你程式加的箱子、桌子）＋ Octomap（從深度相機點雲即時建的體素地圖）。
  3. Allowed Collision Matrix (ACM)：一張布林矩陣，標記哪些 pair 之間的碰撞「允許」。

維護它的是 PlanningSceneMonitor，它訂閱三路資料：/joint_states（機器人動了）、/planning_scene（別人推來的差異更新）、以及 /attached_collision_object（夾到東西了）。

比喻。Planning Scene 是圍棋棋盤的當前局面圖。規劃器是棋手，它只會盯著這張圖想棋。如果圖沒更新（/joint_states 斷了），棋手就會照著三分鐘前的局面下棋——動作看起來完全合理，但會直接撞上剛剛才放上桌的杯子。

RViz 裡的顏色是最好的 debug 工具，務必教學生看懂：

顏色意思
橘色（半透明）你在 RViz 拖出來的 goal state（還沒執行）
灰白/實體機器人的 current state（真實 joint_states）
綠色start state（若你手動改過）
紅色高亮 link正在碰撞的 link——直接告訴你哪兩塊撞了

4. 碰撞檢查：FCL 與 ACM

MoveIt 底層用 FCL(Flexible Collision Library) 做幾何碰撞查詢。檢查一組姿態的成本大致是：

單次碰撞檢查成本 ≈ Npair × Cpair
  • Npair：需要檢查的 link/物件配對數。ACM 停用越多，這個數字越小。一支 8 個 link 的手臂全開是 C(8,2)=28 對，加上世界物件會再乘上去。
  • Cpair：單一配對的幾何檢查成本，跟幾何複雜度直接相關。凸包（box/cylinder/sphere）是常數級，三角網格（mesh）是好幾個數量級的差距。

這解釋了一個實務現象：學生用 SolidWorks 匯出的 50 萬面 mesh 當 collision geometry，規劃時間從 0.2 秒變成 40 秒。正確做法：visual 用漂亮 mesh，collision 用簡化凸包。這是 URDF 有 <visual> 和 <collision> 兩個獨立標籤的全部理由。

學生常見誤解。「規劃出來的路徑一定不會碰撞。」不完全對。規劃器是離散取樣檢查路徑上的點（由 longest_valid_segment_fraction 控制取樣密度）。如果這個參數設太大、障礙物又很薄（例如一片牆），路徑可能「穿牆而過」而檢查不出來——術語叫 tunneling。這是實機撞機的經典死因之一。

5. OMPL 與取樣式規劃：為什麼不用 A*

它解決什麼問題。Nav2 的 A* 在 2D 網格上跑得很好，因為狀態空間只有兩三維。手臂的 configuration space（C-space）是每個關節一個維度：

網格法的狀態數 = kn
  • n：自由度數（Panda 是 7）。
  • k：每個關節切幾格。

就算每個關節只切 10 格（角度解析度粗到 36°，根本不能用），7 軸也是 107 = 一千萬個狀態；切 100 格就是 1014。這就是 curse of dimensionality：網格法在高維度直接死掉。

取樣式規劃（sampling-based planning）的解法是：不建完整地圖，只在 C-space 裡隨機丟點，檢查點是否無碰撞，把可連的點連起來成一棵樹，直到樹碰到目標。

比喻。你在一個伸手不見五指的大山洞裡要找出口。A* 是「把整個山洞畫成方格地圖再搜尋」——山洞太大畫不完。RRT 是「站在原地隨便往一個方向丟一根繩子，能拉直就沿著繩子走一步，站到新位置再丟」。丟夠多次，總會有一根繩子搭到出口。它不保證最短，但保證只要有解、丟到無限次就會找到（這叫 probabilistic completeness，機率完備）。

RRT-Connect（MoveIt Humble 的預設 planner）的關鍵改良：同時從起點和終點各長一棵樹，每次交替長，並且每次都嘗試把兩棵樹接起來。雙向搜尋讓需要的取樣數大幅下降，這是它成為預設值的原因。

常見 OMPL planner 對照：

Planner特性什麼時候用
RRT-Connect雙向、非常快、路徑醜預設，追求「找得到」
RRT*漸進最佳（asymptotically optimal），給多少時間就優化多久要求路徑品質、可以等
PRM先建 roadmap，之後同一場景重複查詢很快環境固定、多次規劃
BiTRRT / KPIECE處理有代價地形/狹窄通道特殊情況
學生常見誤解（本日最重要）。「我按兩次 Plan，結果路徑不一樣，是不是壞了？」沒壞，這是設計。取樣是隨機的，每次結果都不同，而且都不是最佳解。這帶出三個必須教的推論：
① 手臂做出「先繞到後面再回來」的怪動作是正常的，那是 RRT 隨機性 + 只做了 simplification 的結果。
② demo 時千萬不要假設路徑可重現——示範前一定要先 Plan 看預覽，確認合理再 Execute。
③ 要穩定可重現的路徑，就不要用 OMPL，改用 Cartesian path 或 Pilz industrial motion planner（明天 Day 16 會碰到）。

6. 規劃管線：request adapter 與時間參數化

OMPL 吐出來的東西其實只有一串關節角（path），沒有時間。從 path 變成可執行的 trajectory，中間有一整條 planning pipeline，由「adapter」串起來：

  1. FixStartStateBounds：真實機器人的 joint 常常因為編碼器誤差超出 URDF 極限 0.001 rad，規劃器會直接拒絕。這個 adapter 把它夾回範圍內。沒有它，實機幾乎規劃不動。
  2. FixStartStateCollision：起始姿態就在碰撞中時，微調一點點試著脫離。
  3. （規劃）OMPL 產生無碰撞 path。
  4. Simplification / shortcutting：把明顯繞路的段落拉直。
  5. AddTimeOptimalParameterization (TOTG)：這一步才產生時間。在滿足每個 joint 的速度/加速度上限下，算出走完每個 waypoint 的時刻。

所以 velocity_scaling_factor = 0.1 這個參數改的是第 5 步，不是規劃本身——它只是把時間軸拉長。教學上這條界線要講清楚：規劃決定「走哪條路」，時間參數化決定「走多快」，兩件事完全分開。

7. 執行：move_group 怎麼變成馬達指令

最後一段路是 moveit_simple_controller_manager：它讀 moveit_controllers.yaml，把 trajectory 包成 control_msgs/action/FollowJointTrajectory goal，送給 ros2_control 那邊的 joint_trajectory_controller（Day 13 學過），由它做插值並丟給 hardware interface。

完整資料流（背下來，這是助教必考題）：

你的程式 / RViz
      │  goal (pose or joint values)
      ▼
 /move_action  (ROS2 Action)
      ▼
 ┌──────────── move_group ────────────┐
 │ PlanningSceneMonitor               │◄── /joint_states
 │   ├ RobotState  ├ World  ├ ACM     │◄── /planning_scene

 │ Planner Plugin  (OMPL/RRT-Connect) │

                │ FollowJointTrajectory (Action)
                ▼

                ▼
        hardware_interface → 馬達

8. Isaac Sim 5.1 與 USD（晚上的暖身概念）

它解決什麼問題。Gazebo Classic 的渲染是「能看」等級，物理是剛體導向。但 Day 19–20 要做 Sim2Real 和 domain randomization，需要照片級渲染（讓相機影像在模擬與真實之間差距夠小）和GPU 平行環境（RL 訓練要同時跑幾千個機器人）。Isaac Sim 建在 NVIDIA Omniverse 上，用 USD(Universal Scene Description) 當場景格式。

USD 的關鍵概念：它是「圖層堆疊」而不是單一檔案。你可以有一個 base 場景層，再疊一層改材質、再疊一層改光照，彼此不覆寫原檔（叫 composition arcs）。這就是 domain randomization 能做得很乾淨的底層原因。

學生常見誤解。「Isaac Sim 可以取代 Gazebo，所以我直接學 Isaac 就好。」不建議。Isaac Sim 對硬體要求高（需要 RTX GPU、大量 VRAM 與磁碟）、第一次啟動 shader 編譯要 10–30 分鐘、而且 ROS2 bridge 的設定比 Gazebo 麻煩得多。課堂上 Gazebo 仍是主力，Isaac 只在 RL / 高擬真視覺的單元用。學生電腦跑不動時的備案是 MuJoCo（Day 20 會給）。

E. 用 Python 加一個碰撞物件（明天的前菜，今天先跑過）

# ~/ws_moveit/src/day15_demo/day15_demo/add_box.py
# 直接發佈到 /planning_scene，不需要 moveit_py，最少依賴的做法。
import rclpy
from rclpy.node import Node
from moveit_msgs.msg import PlanningScene, CollisionObject
from shape_msgs.msg import SolidPrimitive
from geometry_msgs.msg import Pose


class AddBox(Node):
    def __init__(self):
        super().__init__('add_box')
        # PlanningScene 是 latched 概念，用 transient_local 讓 move_group 一定收得到
        self.pub = self.create_publisher(PlanningScene, '/planning_scene', 10)
        self.timer = self.create_timer(1.0, self.publish_once)
        self.done = False

    def publish_once(self):
        if self.done:
            return

        obj = CollisionObject()
        # frame_id 必須是 move_group 認得的 frame（Panda 的 root 是 panda_link0）
        obj.header.frame_id = 'panda_link0'
        obj.id = 'table_box'

        box = SolidPrimitive()
        box.type = SolidPrimitive.BOX
        box.dimensions = [0.4, 0.4, 0.02]   # x, y, z 長寬高（公尺）

        pose = Pose()
        pose.position.x = 0.5   # 手臂前方 50 cm
        pose.position.y = 0.0
        pose.position.z = 0.2   # 桌面高度
        pose.orientation.w = 1.0  # 沒有這行 quaternion 全 0 = 非法，MoveIt 會拒收

        obj.primitives.append(box)
        obj.primitive_poses.append(pose)
        obj.operation = CollisionObject.ADD

        scene = PlanningScene()
        scene.world.collision_objects.append(obj)
        scene.is_diff = True    # 關鍵：差異更新，不是整份覆寫掉現有場景

        self.pub.publish(scene)
        self.get_logger().info('已送出 table_box，回 RViz 看綠色方塊有沒有出現')
        self.done = True


def main():
    rclpy.init()
    node = AddBox()
    rclpy.spin_once(node, timeout_sec=3.0)
    rclpy.spin_once(node, timeout_sec=3.0)
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

🎓 助教筆記：今天學生最容易卡的 5 個點

1. RViz 開了，但左邊沒有 MotionPlanning 面板

現象：Displays 裡 Add 之後找不到 MotionPlanning，或 RViz 一啟動就閃退。

診斷：

ros2 pkg prefix moveit_ros_visualization   # 空的 = 沒裝
echo $LD_LIBRARY_PATH | tr ':' '\n' | grep -c humble

解法：sudo apt install ros-humble-moveit-ros-visualization，然後開全新 terminal 重新 source。另一個常見原因是學生在同一個 terminal 裡先 source 了自己的 workspace 又 source 了 /opt/ros，順序反了導致抓到舊的 RViz plugin。標準答案：關掉所有 terminal，開新的，只 source 一次。

2. "Unable to sample any valid states for goal tree"

翻譯成人話：規劃器連一個合法的目標關節姿態都取樣不到。幾乎不是規劃器的問題，是目標本身有病。

三個依序檢查的原因：

  1. 目標超出工作空間——IK 無解。RViz 裡看橘色分身有沒有跟著互動球走；不跟就是無解。
  2. 目標姿態本身在碰撞中——例如目標點在桌子裡面。RViz 會把撞到的 link 標紅。
  3. 目標超出 joint limits——orientation 要求手腕轉超過極限。試著只給 position tolerance、放寬 orientation（RViz 的 Planning 分頁可調 Goal Tolerance）。

教學話術：「這個錯誤是規劃器在說『你給我的目的地不存在』，不是『我找不到路』。先確認目的地合不合法，再談路。」

3. Plan 成功，按 Execute 沒反應 / 立刻回 ABORTED

這是最耗時間的一類，因為錯誤訊息在 move_group terminal，學生只看 RViz。

典型訊息：Unable to identify any set of controllers that can actuate the specified joints 或 Failed to find controller for group。

診斷 SOP：

# 1) 控制器 action server 存在嗎？
ros2 action list | grep follow_joint_trajectory

# 2) 控制器活著嗎？
ros2 control list_controllers

# 3) 名字對得上嗎？把下面兩份的 joint 名單逐字比對
ros2 param get /move_group robot_description_semantic | grep -A5 "

根因九成是：moveit_controllers.yaml 裡寫的 controller 名稱 / joint 名單，跟 ros2_control 實際載入的對不上一個字（常見是多了或少了 panda_ 前綴）。要求學生把兩份 YAML 並排貼在螢幕上逐行對，比盲猜快十倍。

4. 機器人在 RViz 是「橘色半透明的漂浮狀態」，或整個歪掉

根因：沒有 /joint_states，Planning Scene 的 RobotState 一直是預設值。

ros2 topic hz /joint_states      # 沒輸出 = 沒人在發
ros2 node info /move_group | grep -i joint_states
ros2 run tf2_tools view_frames   # 看 TF tree 有沒有斷

解法：demo 模式下應該由 joint_state_broadcaster（fake controller）發佈。實機則是 driver 沒起來。順便複習 Day 5：MoveIt 高度依賴 TF，TF tree 一斷，MoveIt 什麼都做不了——這是 Day 5 那三大死法在手臂上的翻版。

5. 規劃超級慢（每次 3–5 秒），或每次路徑都很怪

慢的原因幾乎都是 collision geometry 用了高面數 mesh。診斷：把 URDF 裡 <collision> 的 mesh 暫時換成 box，速度立刻回來就確診。

路徑怪的原因是 RRT 的隨機性。可以做的三件事：

  1. 把 Planning Attempts 從 1 調到 10（多規劃幾次取最好的）。
  2. 換 planner：RViz 的 Planning 分頁下拉選 RRTstar，並把 planning time 拉到 5–10 秒。
  3. 需要「直線移動」時根本不該用 OMPL——改用 Cartesian path（明天 Day 16 主題）。

教學重點：學生看到怪路徑第一反應是「MoveIt 壞了」。要讓他理解「找得到 ≠ 找得好」是取樣式規劃的本質特徵，不是 bug。

加碼：Isaac Sim 開不起來

  • 黑畫面 / 秒退：九成是 GPU 驅動太舊或不是 RTX 卡。先跑 nvidia-smi。
  • 卡在啟動畫面十幾分鐘：正常，第一次要編譯 shader cache。第二次啟動會快很多。先別 Ctrl-C。
  • WSL2 / 遠端連線：Isaac Sim 的 GUI 在 WSL 或 X11 forwarding 下問題很多，建議直接在有實體螢幕的 Ubuntu 上跑。
  • pip install 找不到版本：先 pip index versions isaacsim --extra-index-url https://pypi.nvidia.com 查實際可用版本，再填進去。
