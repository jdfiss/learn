📖 知識點逐個講解

1. Node（節點）— 為什麼要把程式切碎？

它解決什麼問題 一台機器人要同時做：讀雷射、算定位、規劃路徑、控馬達、看攝影機。如果全寫在一支 main.py 裡，任何一個地方當掉整台車就停了，而且你沒辦法只重啟「攝影機那段」。Node 把系統切成一個個可以獨立啟動、獨立當掉、獨立重寫的行程單位。

白話：Node 就是「一個負責一件事的小程式」，它自己有名字（例如 /turtlesim），並且透過網路跟別的 node 講話。

比喻：一家公司裡的員工。每個人只做自己那份工作，靠公佈欄（Topic）和打電話（Service）協作。老闆換掉會計，業務照樣上班——這就是 node 的價值。

學生常見誤解 「一個 node = 一個 process」。不一定。ROS2 可以用 component（rclcpp_components）把多個 node 塞進同一個 process 共享記憶體（zero-copy），這是 ROS2 相對 ROS1 nodelet 的正規做法。另一個方向：一個 process 也可以 spin 好幾個 node。所以看到 ros2 node list 有 5 個名字，不代表有 5 個 python3 行程。

2. Topic（話題）— 非同步的廣播

它解決什麼問題 雷射 10Hz 一直吐資料，可能有 3 個模組要用（SLAM、避障、記錄）。如果用「誰要就跟我要一次」的模式，雷射節點要認識所有人、寫 3 份程式。Topic 讓發布者完全不知道有誰在聽，聽的人自己來訂閱——這叫「解耦」。

白話：Publisher 把訊息貼上公佈欄（topic 名稱，例如 /scan），任何 Subscriber 訂閱該欄位就會收到。多對多、非同步、不等回應。

比喻：廣播電台。DJ 不知道有幾個人在聽，也不會因為沒人聽就停播；你半路轉到這台，前面播過的你就是沒聽到。這個「前面播過的聽不到」正是後面 Durability 要處理的事。

每個 topic 有固定的訊息型別（message type），例如 sensor_msgs/msg/LaserScan。型別對不上就完全不會連上——ROS2 不會幫你轉。

學生常見誤解 「我 publish 了，對方就一定收得到。」錯。至少三種情況會掉：(a) 訂閱者還沒起來（topic 沒有記憶，預設 VOLATILE）；(b) QoS 不相容，根本沒配對成功；(c) 用 BEST_EFFORT + 網路壅塞，封包就是丟了。Topic 是「盡力送達的廣播」，不是「保證送達的訊息佇列」。

3. Service（服務）— 同步的一問一答

它解決什麼問題 有些事情是「我問你一次，你回我一個答案，我要等到答案才能繼續」——例如「幫我把地圖存檔」「把烏龜傳送到 (5,5)」。用 topic 做要自己配對 request/response、自己處理逾時，很笨。Service 直接封裝成 RPC。

白話：Client 送 Request → Server 處理 → 回 Response。一對一，要在短時間內做完（毫秒到一兩秒）。

比喻：打電話問櫃檯「還有房間嗎」。你會在線上等答案，所以對方不能拿著話筒去掃地掃十分鐘。

學生常見誤解 ⚠️ 這題很會考 在一個 subscriber callback 裡面呼叫 service 並且用 spin_until_future_complete() 等結果 → 直接死鎖（deadlock），程式卡住不動也不報錯。原因：預設的單執行緒 executor 正在跑你的 callback，它沒辦法同時去處理 service 的回應。解法：改用 MultiThreadedExecutor + ReentrantCallbackGroup，或改成 async/callback 寫法。這是 Day 3 之後學生第一批哀嚎的來源，先記住症狀。

4. Action（動作）— 做很久、要回報、可以喊卡

它解決什麼問題 「導航到門口」要跑 40 秒。用 service：你會卡住 40 秒、中途不知道走到哪、想取消也取消不了。Action 就是為「長時間任務」設計的。

白話：Action 有三個部分：
Goal（我要你去 (3,4)）→ Feedback（持續回報：還剩 2.1 公尺）→ Result（到了／失敗）。而且隨時可以 cancel。

比喻：叫外送。你下單（goal）、App 一直顯示外送員位置（feedback）、最後送達或取消（result / cancel）。

底層真相（助教要知道） Action 不是新的通訊機制，它是用 Topic + Service 組出來的：2 個 service（send_goal、cancel_goal、get_result 實際是 3 個）+ 1~2 個 topic（feedback、status）。所以 ros2 topic list --include-hidden-topics 會看到 /navigate_to_pose/_action/feedback 這種底線開頭的隱藏 topic。學生問「為什麼 Nav2 的 topic 前面有底線」就是這個。
學生常見誤解 「Action 比較強，那全部都用 Action。」不對。Action 的 overhead 大、程式碼囉嗦得多。判斷標準只有一個：這件事會不會超過大約 1 秒、需不需要中途取消或看進度？是 → Action；否 → Service。

5. Parameter（參數）— 節點身上的旋鈕

它解決什麼問題 「最大速度 0.5 m/s」寫死在程式裡，調一次就要重新 build。Parameter 讓你在啟動時用 YAML 給、執行中用指令改。

白話：Parameter 是屬於某個 node 的具名、有型別的設定值（bool / int / double / string / 陣列）。node 要先 declare_parameter() 宣告，才能讀寫。

比喻：機器背面的 DIP 開關或旋鈕。開機前可以先撥好（YAML），開機後也能轉（ros2 param set）。

學生常見誤解 「Parameter 是全域變數，設一次大家都吃得到。」錯得很嚴重。Parameter 依附在單一 node 上，/node_a 和 /node_b 各有各的 max_speed，互不影響。（ROS1 的 Parameter Server 才是全域的，這是 ROS1→ROS2 最容易搞混的一點。）另外：ROS2 沒有中央 parameter server，node 死了參數就沒了，所以要 ros2 param dump 存檔。

6. QoS（Quality of Service）— ROS2 最大的坑，也是今天的重點

它解決什麼問題 ROS1 的通訊底層是 TCP，一律保證送達。但機器人上有兩種完全相反的需求：
• 相機影像 30Hz：寧可丟掉舊的一張，也不要為了重傳而卡住（丟了下一張馬上來）
• 地圖 /map：只發一次，晚到的訂閱者也一定要拿到
一套設定不可能同時滿足。ROS2 底層改用 DDS，把「傳輸行為」開放成可設定的 QoS profile。

相容性規則（背起來，這是診斷的核心）

Publisher 的承諾 必須「≥」 Subscriber 的要求，才能配對成功。

Reliability：  RELIABLE(強) > BEST_EFFORT(弱)
Durability ：  TRANSIENT_LOCAL(強) > VOLATILE(弱)
PublisherSubscriber結果
RELIABLERELIABLE✅ 連上
RELIABLEBEST_EFFORT✅ 連上（我承諾更多，你要求較少，OK）
BEST_EFFORTBEST_EFFORT✅ 連上
BEST_EFFORTRELIABLE❌ 完全收不到（我做不到你要求的保證）

比喻：徵才。職缺要求「碩士以上」（Subscriber 要求 RELIABLE），你是碩士或博士都能錄取；你只有學士（BEST_EFFORT）就是不錄取。而且——ROS2 不會幫你降級湊合，它就是不連。

學生常見誤解 ⚠️ 全課程 Top 3 卡點 「ros2 topic list 有這個 topic、ros2 topic hz 也有數字，所以資料是通的。」不一定。topic list 只是 discovery 層看得到名字，跟你的 subscriber 能不能收到是兩回事。判斷唯一標準是 ros2 topic info /xxx --verbose 看雙方的 QoS，以及終端機有沒有跳 incompatible QoS 警告。

7. DDS 與 Discovery — 為什麼沒有 roscore 也找得到彼此

ROS2 底層是 DDS（預設 Humble 用 Fast DDS）。開機時每個 node 會往區域網路發 multicast（多播）封包宣告「我在這、我發這些 topic」，別人聽到就直接建立點對點連線。所以 ROS2 沒有 master、沒有單點故障。

ROS_DOMAIN_ID（0~101，預設 0）是「頻道號碼」：同一個網段上，只有 domain ID 相同的 node 才看得到彼此。教室裡 20 個學生共用同一個 Wi-Fi 時，如果大家都用預設 0，會互相看到對方的 /cmd_vel，別人的車就會亂動。這是 Day 24 實體機器人的必考題，今天先建立概念。

8. ROS2 vs ROS1 — 講給有 ROS1 背景的人聽

Step 7.（選做，10 分鐘）讀懂一段設定 QoS 的 rclpy 程式

Day 3 才會正式寫 node，今天只要「看得懂」即可。

import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy, DurabilityPolicy, HistoryPolicy
from std_msgs.msg import String

class QoSDemo(Node):
    def __init__(self):
        super().__init__('qos_demo')

        # 宣告參數：ROS2 一定要先 declare 才能 get，否則丟 ParameterNotDeclaredException
        self.declare_parameter('publish_rate', 2.0)
        rate = self.get_parameter('publish_rate').value

        # 感測器串流常用的 QoS：丟了就算了、只留最新一筆
        sensor_qos = QoSProfile(
            reliability=ReliabilityPolicy.BEST_EFFORT,  # 不重傳，低延遲
            durability=DurabilityPolicy.VOLATILE,       # 晚來的訂閱者拿不到舊資料
            history=HistoryPolicy.KEEP_LAST,
            depth=1,                                    # 緩衝區只留 1 筆
        )

        # 地圖 / 靜態資訊常用的 QoS：晚來的人也要補送（等同 ROS1 的 latched topic）
        map_qos = QoSProfile(
            reliability=ReliabilityPolicy.RELIABLE,
            durability=DurabilityPolicy.TRANSIENT_LOCAL,  # ← 關鍵
            history=HistoryPolicy.KEEP_LAST,
            depth=1,
        )

        self.pub = self.create_publisher(String, 'qos_demo_topic', sensor_qos)
        self.create_timer(1.0 / rate, self.tick)

    def tick(self):
        msg = String()
        msg.data = f'stamp={self.get_clock().now().nanoseconds}'
        self.pub.publish(msg)

def main():
    rclpy.init()
    rclpy.spin(QoSDemo())   # spin = 把控制權交給 ROS，開始處理 callback

if __name__ == '__main__':
    main()

🎓 助教筆記：學生今天最會卡的 5 個問題

卡點 1｜ros2: command not found ／ Package 'turtlesim' not found 錯誤訊息：bash: ros2: command not found 或 Package 'demo_nodes_cpp' not found
真正原因：新開的終端機沒有 source。這佔第一週所有問題的一半以上。
診斷指令：
printenv ROS_DISTRO          # 空的 → 就是沒 source
printenv | grep AMENT         # 空的 → 同上
解法：source /opt/ros/humble/setup.bash，並教學生寫進 ~/.bashrc。
助教講法：「ROS 不是安裝在系統路徑裡的普通指令，它是一組環境變數。每開一扇新的門（terminal），你都要重新報到一次。」
卡點 2｜topic 明明有，echo 卻一片空白 ★最有價值的一題 症狀：ros2 topic list 看得到、ros2 topic hz 甚至有數字，但 ros2 topic echo 完全沒東西。
錯誤訊息（有時才會出現）：New publisher discovered on topic 'X', offering incompatible QoS. No messages will be sent to it. Last incompatible policy: RELIABILITY
三種可能，照順序排除：
  1. QoS 不相容（最常見）：ros2 topic info /X --verbose，比對 Publisher 與 Subscription 的 Reliability / Durability。感測器 topic 要加旗標：ros2 topic echo /scan --qos-reliability best_effort。
  2. 名稱空間打錯：/scan vs /robot1/scan。用 ros2 topic list | grep scan 確認完整路徑。
  3. publisher 其實沒在發：ros2 topic hz /X 若印出 no new messages，問題在發布端不在接收端。
SOP 一句話：list → hz → info -v，三招定位。
卡點 3｜ros2 service call 按下去就卡死，游標不動 症狀：終端機停在 waiting for service to become available...。
診斷：
ros2 service list | grep <名字>      # service 到底存不存在？
ros2 node list                       # 提供這個 service 的 node 起來了嗎？
ros2 service type /your_service      # 型別對不對？
三種原因：(a) server node 根本沒啟動；(b) service 名字打錯或少了 namespace；(c) request 的 YAML 欄位名稱或型別寫錯（例如 x: 3 寫成整數，但欄位是 float，要寫 3.0）。
進階（Day 3 之後才會遇到）：在 callback 裡同步呼叫 service 造成的 executor 死鎖，症狀是完全沒有錯誤訊息的凍結。看到「沒報錯就是不動」，先問「你是不是在 callback 裡面 call service？」
卡點 4｜ParameterNotDeclaredException 錯誤訊息：rclpy.exceptions.ParameterNotDeclaredException: ('Invalid access to undeclared parameter(s)', ...)
原因：ROS2 預設不允許存取未宣告的 parameter（ROS1 的習慣直接用會死在這）。
解法：在 __init__ 裡先 self.declare_parameter('name', default_value)。
另一個變形：ros2 param set 說 Setting parameter failed: parameter 'xxx' has invalid type → 型別要一致，宣告成 double 就必須用 1.0 不能用 1。
卡點 5｜看得到自己的 node，看不到同學／另一台電腦的 症狀：兩台電腦跑同一個系統，ros2 node list 只看得到自己。或反過來：看到一堆不屬於自己的 node。
診斷：
printenv ROS_DOMAIN_ID       # 兩台必須一樣
ros2 daemon stop && ros2 daemon start   # 清掉快取殘影
ros2 multicast receive        # 一台跑這個
ros2 multicast send           # 另一台跑這個 → 收得到才代表網路 OK
ip addr                       # 兩台在不在同一網段
常見成因：(a) ROS_DOMAIN_ID 不同；(b) 防火牆擋 multicast（sudo ufw disable 測試）；(c) 學校 Wi-Fi 隔離客戶端（AP isolation）——這個無解，要改用有線或自己的路由器；(d) Docker 沒開 --network host。
教室預防措施：開學第一天就規定每個學生用自己的 ROS_DOMAIN_ID（例如學號末兩碼，範圍 0–101），寫進 .bashrc。這件事現在不做，Day 24 上實體機時會出人命等級的混亂。
