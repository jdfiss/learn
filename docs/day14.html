A-1　Day 8 回顧：Gazebo 與 TurtleBot3 的四條主幹 Topic

它解決什麼問題：你不可能一開始就用真機練習——撞壞了要修，電池要充，環境不可重現。 模擬器提供一個可重來、可存檔、可以故意搞壞的世界。而 ROS2 的設計讓「模擬」和「真機」對上層程式而言長得一模一樣： 只要 Topic 名稱與型別相同，Nav2 根本分不出下面接的是 Gazebo 還是實體 TurtleBot3。這就是 Sim2Real 之所以可行的第一層基礎。

比喻：Topic 就像醫院裡的病床監視器。/scan 是眼睛，/odom 是「我自己覺得走了多遠」的體感， /tf 是全身骨架的相對位置表，/cmd_vel 是你對肌肉下的命令。醫生（Nav2）只看螢幕、只下醫囑，不在乎病人是真人還是假人模型。

Topic型別誰發布誰訂閱一句話
/scansensor_msgs/LaserScan雷射驅動 / Gazebo pluginSLAM、Nav2 costmap一圈 360 個距離值，含 angle_min、angle_increment、ranges[]
/odomnav_msgs/Odometry差速輪驅動AMCL、controller輪子編碼器積分出來的位置，會漂移，短期準、長期歪
/cmd_velgeometry_msgs/TwistNav2 controller / teleop底盤驅動只有 linear.x 與 angular.z 對差速輪有意義
/tftf2_msgs/TFMessage多個節點各發一段幾乎所有節點map→odom（AMCL 發）、odom→base_link（里程計發）、base_link→laser（URDF 發）
常見誤解：「/odom 不準，那把它關掉直接用 AMCL 就好」 錯。AMCL 的粒子濾波需要 odom 當作預測步（prediction step）的運動模型輸入。沒有 odom，AMCL 每一輪都只能靠雷射盲猜， 會抖到無法使用。odom 的角色不是「提供正確位置」，而是「提供短時間內可信的位移增量」；長期誤差由 AMCL 用地圖來修正。 這正是 map → odom → base_link 三層 tf 的存在理由：map→odom 這一段就是「累積漂移的修正量」。

A-2　Day 9 回顧：SLAM 的一句話與一條公式

它解決什麼問題：要導航必須先有地圖，但要畫地圖必須先知道自己在哪——這是一個雞生蛋問題。 SLAM（Simultaneous Localization and Mapping）就是同時解這兩件事。

核心公式（Occupancy Grid 的 log-odds 更新）：

l(m_i | z_{1:t}) = l(m_i | z_{1:t-1}) + inverse_sensor_model(m_i, z_t) - l_0
l(·)log-odds，即 log(p / (1-p))。用它是因為加法比乘法快、而且不會數值下溢；機率連乘幾百次會變成 0。
m_i第 i 個格子（cell）。整張地圖被切成一格一格，每格獨立估計「這裡有障礙物」的機率。
z_{1:t}從開始到現在的所有雷射觀測。
inverse_sensor_model「這一次雷射打到了什麼」轉成的證據量：光束打中的格子 +（更相信有東西），光束穿過的格子 −（更相信是空的）。
l_0先驗值。地圖初始化時全部設成「不知道」，也就是 p = 0.5、l_0 = 0。減掉它是為了不重複計入先驗。

比喻：每個格子有一個「有障礙物」的信用分數。雷射每掃一次就是一次投票，打到就加分、穿過就扣分。 掃了幾百次以後，牆壁的格子分數會非常高，空地非常低，沒掃到的地方維持 0（未知，在 rviz2 顯示成灰色）。

Loop closure（迴環偵測）：機器人繞了一大圈回到起點，但因為漂移，它以為自己在別的地方，於是把同一面牆畫了兩次（地圖出現「鬼影」/重影）。 Loop closure 就是認出「我來過這裡」，然後把整條軌跡往回拉平（pose graph optimization）。 slam_toolbox 的地圖突然「跳一下、變整齊」，那一瞬間就是 loop closure 觸發了。

常見誤解：「地圖歪掉是雷射不準」 九成不是。地圖歪掉的排序原因是：(1) 推車／走路太快，掃描比對跟不上；(2) 原地快速旋轉（旋轉是 SLAM 最難的動作）； (3) 走廊、空曠大廳這種幾何特徵不足的環境，掃描長得都一樣，比對無從下手；(4) 才輪到雷射本身。 給學生的口訣：「慢慢走、少原地轉、多繞經有特徵的角落、記得回到起點閉環」。

A-3　Day 10–11 回顧：Nav2 資料流（今天一定要能默畫）

請先閉上眼睛講一遍，再看下面對答案。

使用者 / 你的程式
   │  NavigateToPose action goal（geometry_msgs/PoseStamped）
   ▼
[ bt_navigator ]  ← 讀 behavior tree XML，決定「流程」
   │  它是總指揮，不算路徑、不發速度，只按劇本呼叫下面的人
   ├─► [ planner_server ]    global costmap + A*/NavFn/Smac → nav_msgs/Path（全域路徑）
   ├─► [ controller_server ] local costmap + DWB/RPP → geometry_msgs/Twist（/cmd_vel）
   └─► [ behavior_server ]   卡住時的 recovery：spin / backup / wait / clear costmap
   ▲
   │  「我在哪」
[ amcl ] ── 用 /scan 比對 map，輸出 map→odom 的 tf 修正量
[ map_server ] ── 提供靜態地圖 /map
[ costmap_2d ] ── 靜態層 + 障礙層 + 膨脹層，疊出「哪裡不能走」

五個角色，一句話各記一句

  • bt_navigator：導演。只決定「先做什麼、失敗了做什麼」，本身不做計算。
  • planner_server（全域規劃）：看整張地圖，畫一條從 A 到 B 的路。不管動態障礙、不管機器人現在的速度。
  • controller_server（區域控制）：只看機器人周圍幾公尺，負責「貼著全域路徑走、同時閃開突然出現的人」，輸出速度指令。
  • costmap：把地圖變成「代價」。0 = 完全自由、254 = 致命障礙（lethal）、253 = inscribed（機器人中心進去必撞）、255 = unknown。
  • AMCL：粒子濾波定位。撒一堆「機器人可能在這」的假設點，用雷射比對淘汰不合理的，逐漸收斂。
Day 11 的五大死因，今天再默背一次
  1. tf 沒接起來：map → odom → base_link → laser 斷任一節，Nav2 完全不動且刷 "Timed out waiting for transform"。
  2. 初始位姿沒給：AMCL 不知道機器人在哪，粒子散開，機器人原地亂轉。rviz2 要按 2D Pose Estimate。
  3. inflation_radius 太大：門口、走廊整個被膨脹層填滿變成不可通行，planner 回 "Failed to create plan"。
  4. lifecycle 節點沒 activate：節點在但狀態是 unconfigured/inactive，行為像「啟動了卻沒反應」。
  5. 模擬時間沒對齊：Gazebo 下每個節點都要 use_sim_time:=true，漏一個就 tf 時間戳對不上。

A-4　Day 12–13 回顧：運動學與控制的三個關鍵詞

FK（順向運動學）：給我每個關節角度 q，算出手爪在空間中的位置與姿態。唯一解，一定算得出來，就是一連串齊次變換矩陣相乘。

IK（逆向運動學）：給我手爪想去的位置，回推每個關節該轉幾度。可能無解（超出工作範圍）、可能多解（手肘朝上或朝下都能到）。 這是為什麼 MoveIt2 要「規劃」而不是「計算」。

Jacobian（雅可比矩陣）：連接「關節速度」與「末端速度」的橋樑。

v = J(q) · q̇
v末端執行器的速度（6 維：三個平移 + 三個旋轉）。
q̇各關節的角速度（n 維，n = 關節數）。
J(q)6×n 矩陣，它的值隨當下姿態 q 改變——這是重點，Jacobian 不是常數。

奇異點（singularity）：某些姿態下 J 掉秩（det → 0），意思是「末端有某個方向怎麼動關節都動不出去」。 反過來，若你要求末端往那個方向動一點點，IK 解出來的關節速度會衝到無限大——真機上表現成手臂突然暴衝。 比喻：像手臂完全打直時想再往前伸 1 公分，肩肘怎麼轉都辦不到，硬要就只能瘋狂亂扭。

動力學方程：

M(q)·q̈ + C(q, q̇)·q̇ + G(q) = τ
M(q)慣性矩陣。手臂伸得越開，等效慣性越大，越難加速——所以 M 跟姿態有關。
C(q,q̇)科氏力與離心力項。只有在「動起來」時才存在，速度越快影響越大。
G(q)重力項。手臂靜止不動也需要出力，就是在對抗它。
τ各關節馬達要輸出的力矩。
常見誤解：「PID 調好就夠了，不用管重力補償」 在低速、輕負載時勉強成立；一旦手臂伸長或抓重物，PID 為了對抗重力必須靠「累積誤差」把 I 項拉起來， 結果就是穩態下垂 + 動作起步時暴衝（integral windup）。 正確做法是把 G(q) 當前饋（feedforward）直接補進去，讓 PID 只需要處理「模型算不準的殘差」。 這就是 computed torque control 的核心思想：先用模型算大部分，PID 只收尾。

Part B · 下午：Nav2 多點巡航實作

它解決什麼問題：到目前為止你都是在 rviz2 上用滑鼠點 2D Goal Pose。 但實務上（送餐機器人、巡邏機器人、課程專題）需要的是程式自動依序走訪多個點、失敗要能處理、隨時可以叫停。 nav2_simple_commander 就是 Nav2 官方提供的 Python 包裝，把底層繁瑣的 action client 收成幾個好懂的方法。

比喻：直接寫 action client 像自己組電腦（要處理 goal handle、feedback callback、result future、cancel）； BasicNavigator 像買品牌機——功能少一點，但 90% 的課堂需求它都夠用，而且學生看得懂。

B-1　BasicNavigator 的核心方法

方法作用注意
waitUntilNav2Active()擋住程式，直到 Nav2 所有 lifecycle 節點都 active一定要呼叫，否則太早送 goal 會直接被丟掉
setInitialPose(pose)程式化地給 AMCL 初始位姿，等同 rviz2 的 2D Pose Estimate用 slam_toolbox 即時建圖時不要呼叫
goToPose(pose)送單一目標點，非阻塞送完要自己輪詢 isTaskComplete()
followWaypoints(poses)丟一整串航點，Nav2 內部自己依序走簡單但失敗時無法針對單點重試
isTaskComplete()問「這次任務結束了沒」回 False 時順便會更新 feedback，所以一定要在迴圈裡呼叫
getFeedback()取得剩餘距離、已花時間、recovery 次數欄位名稱是 distance_remaining、navigation_time
getResult()回傳 TaskResult.SUCCEEDED / CANCELED / FAILED必須檢查，不要假設一定成功
cancelTask()中止當前任務逾時保護就靠它

建立檔案 ~/patrol_min.py：

#!/usr/bin/env python3
"""最小可跑版本：走訪 4 個航點。"""
import rclpy
from geometry_msgs.msg import PoseStamped
from nav2_simple_commander.robot_navigator import BasicNavigator, TaskResult


def make_pose(nav, x, y, yaw_deg=0.0):
    """把 (x, y, yaw) 包成 Nav2 要的 PoseStamped。

    Nav2 的 orientation 是 quaternion（四元數），不是角度。
    這裡只繞 Z 軸轉，所以 z = sin(yaw/2)、w = cos(yaw/2)，x = y = 0。
    """
    import math
    p = PoseStamped()
    p.header.frame_id = 'map'                      # 一定是 map，不是 odom
    p.header.stamp = nav.get_clock().now().to_msg()
    p.pose.position.x = float(x)
    p.pose.position.y = float(y)
    p.pose.orientation.z = math.sin(math.radians(yaw_deg) / 2.0)
    p.pose.orientation.w = math.cos(math.radians(yaw_deg) / 2.0)
    return p


def main():
    rclpy.init()
    nav = BasicNavigator()

    # 1) 給初始位姿。若你是用 slam_toolbox 即時建圖，請把這三行註解掉。
    init = make_pose(nav, 0.0, 0.0, 0.0)
    nav.setInitialPose(init)

    # 2) 等 Nav2 全部節點 active。少了這行，goal 會被丟掉而且沒有錯誤訊息。
    nav.waitUntilNav2Active()

    # 3) 航點清單。請換成你自己地圖上的合法座標
    #    （在 rviz2 上把滑鼠移到目標處，左下角會顯示 x/y）
    waypoints = [
        make_pose(nav,  1.5,  0.0,   0),
        make_pose(nav,  1.5,  1.5,  90),
        make_pose(nav,  0.0,  1.5, 180),
        make_pose(nav,  0.0,  0.0, 270),
    ]

    for i, wp in enumerate(waypoints, start=1):
        nav.get_logger().info(f'前往航點 {i}/{len(waypoints)}')
        nav.goToPose(wp)

        while not nav.isTaskComplete():
            fb = nav.getFeedback()
            if fb:
                nav.get_logger().info(
                    f'  剩餘距離 {fb.distance_remaining:.2f} m')

        result = nav.getResult()
        if result == TaskResult.SUCCEEDED:
            nav.get_logger().info(f'航點 {i} 抵達')
        elif result == TaskResult.CANCELED:
            nav.get_logger().warn(f'航點 {i} 被取消')
            break
        else:
            nav.get_logger().error(f'航點 {i} 失敗')

    nav.get_logger().info('巡航結束')
    nav.lifecycleShutdown()
    rclpy.shutdown()


if __name__ == '__main__':
    main()

常見誤解：「isTaskComplete() 只是個查詢，可以不放在迴圈裡」 錯得很致命。isTaskComplete() 內部會 spin 一次 node，feedback 只有在這時候才會被更新。 如果你寫成 time.sleep(1) 然後才呼叫一次，feedback 永遠是 None，而且 action 的通訊會卡住。 規則：「while not nav.isTaskComplete():」這行不能改成別的等待方式。

B-3　加上逾時、重試、優雅取消（可以拿去用在專題上的版本）

上面的版本有三個現實問題：卡住會無限等、失敗就放棄、Ctrl-C 時機器人還在跑。修掉它們：

#!/usr/bin/env python3
"""巡航強化版：逾時保護 + 失敗重試 + Ctrl-C 安全停車。"""
import math
import signal
import sys
import rclpy
from geometry_msgs.msg import PoseStamped
from nav2_simple_commander.robot_navigator import BasicNavigator, TaskResult

TIMEOUT_SEC = 90.0   # 單一航點最長容忍時間，超過就取消
MAX_RETRY = 2        # 每個航點最多重試次數


def make_pose(nav, x, y, yaw_deg=0.0):
    p = PoseStamped()
    p.header.frame_id = 'map'
    p.header.stamp = nav.get_clock().now().to_msg()
    p.pose.position.x = float(x)
    p.pose.position.y = float(y)
    p.pose.orientation.z = math.sin(math.radians(yaw_deg) / 2.0)
    p.pose.orientation.w = math.cos(math.radians(yaw_deg) / 2.0)
    return p


def go_once(nav, wp, idx):
    """送一次 goal，回傳 TaskResult。內含逾時保護。"""
    nav.goToPose(wp)
    while not nav.isTaskComplete():
        fb = nav.getFeedback()
        if fb is None:
            continue
        # Duration msg 轉秒：sec 是整數秒，nanosec 是奈秒
        elapsed = fb.navigation_time.sec + fb.navigation_time.nanosec * 1e-9
        if elapsed > TIMEOUT_SEC:
            nav.get_logger().warn(
                f'航點 {idx} 超過 {TIMEOUT_SEC:.0f} 秒，主動取消')
            nav.cancelTask()
            # 取消是非同步的，要等它真的收工
            while not nav.isTaskComplete():
                pass
            return TaskResult.CANCELED
    return nav.getResult()


def main():
    rclpy.init()
    nav = BasicNavigator()

    # Ctrl-C 時不要讓機器人保持在移動狀態
    def on_sigint(signum, frame):
        nav.get_logger().warn('收到 Ctrl-C，取消導航中…')
        nav.cancelTask()
        nav.lifecycleShutdown()
        rclpy.shutdown()
        sys.exit(0)
    signal.signal(signal.SIGINT, on_sigint)

    nav.setInitialPose(make_pose(nav, 0.0, 0.0, 0.0))
    nav.waitUntilNav2Active()

    waypoints = [
        make_pose(nav,  1.5,  0.0,   0),
        make_pose(nav,  1.5,  1.5,  90),
        make_pose(nav,  0.0,  1.5, 180),
        make_pose(nav,  0.0,  0.0, 270),
    ]

    stats = {'ok': 0, 'fail': 0}
    for i, wp in enumerate(waypoints, start=1):
        for attempt in range(1, MAX_RETRY + 2):     # 第 1 次 + MAX_RETRY 次重試
            nav.get_logger().info(
                f'航點 {i}/{len(waypoints)}（第 {attempt} 次嘗試）')
            result = go_once(nav, wp, i)

            if result == TaskResult.SUCCEEDED:
                nav.get_logger().info(f'✔ 航點 {i} 抵達')
                stats['ok'] += 1
                break

            nav.get_logger().warn(f'✘ 航點 {i} 結果：{result}')
            if attempt > MAX_RETRY:
                stats['fail'] += 1
                nav.get_logger().error(f'航點 {i} 放棄，跳過')
            else:
                # 重試前把 costmap 上的殘留障礙清掉，這是很有效的一招
                nav.clearAllCostmaps()

    nav.get_logger().info(
        f"巡航結束：成功 {stats['ok']} 點、失敗 {stats['fail']} 點")
    nav.lifecycleShutdown()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
為什麼重試前要 clearAllCostmaps()？
Costmap 的障礙層有記憶：一個人走過去被雷射掃到，會在 costmap 上留下障礙標記， 即使人已經離開，只要沒有雷射光束「穿過」那格把它清掉（raytrace clearing），標記就會殘留。 專題現場最常見的「明明沒東西擋，機器人就是說 planner failed」，八成是這個。 清掉 costmap 再試一次，通常就過了。

🎓 助教筆記：本週學生最常卡住的 5 個問題

卡點 1：goal 送出去，機器人完全不動、終端機一直刷 transform 錯誤

錯誤訊息：

[controller_server]: Timed out waiting for transform from base_link to map
  to become available, tf error: Invalid frame ID "map" passed to canTransform

診斷：

ros2 run tf2_ros tf2_echo map odom     # 沒有輸出 → AMCL 沒在跑或沒收到 /scan
ros2 node list | grep amcl
ros2 topic hz /scan

解法：依序確認 (1) amcl 節點存在且 lifecycle 是 active；(2) /scan 有在發； (3) 有沒有在 rviz2 按過 2D Pose Estimate。九成是第 (3) 點。

卡點 2：機器人在原地瘋狂旋轉，就是不出發

沒有錯誤訊息，這是最讓學生崩潰的一種。

診斷：在 rviz2 開啟 /particlecloud 顯示。如果粒子雲是「散開一大片」而不是「聚成一小團」， 代表 AMCL 完全不知道機器人在哪，它正在原地轉圈試圖蒐集資訊來收斂（這其實是 recovery 行為，不是壞掉）。

解法：重新用 2D Pose Estimate 給一個準確的初始位姿，包含朝向—— 學生常常只點對位置、箭頭方向卻拉反了 180 度，這會讓 AMCL 更難收斂。教他們「拖曳箭頭時要看機器人在 Gazebo 裡的正面朝哪」。

卡點 3：Failed to create plan / planner 一直失敗

錯誤訊息：[planner_server]: GridBased plugin failed to plan from (…) to (…): "No valid path found"

診斷順序：

# (a) 目標點是不是落在障礙物或未知區域上？→ rviz2 看 global costmap 那格是不是紫/紅
# (b) 膨脹半徑是不是太大，把通道填滿了？
ros2 param get /global_costmap/global_costmap inflation_layer.inflation_radius
ros2 param get /global_costmap/global_costmap robot_radius

# (c) 先清一次 costmap 再試
ros2 service call /global_costmap/clear_entirely_global_costmap \
    nav2_msgs/srv/ClearEntireCostmap

解法：TurtleBot3 burger 的 robot_radius 約 0.105，inflation_radius 通常設 0.25～0.55。 若學生的地圖是狹窄走廊，把 inflation_radius 降到 0.2 左右通常就通了。 但要同時提醒代價：膨脹太小 → 機器人會貼牆擦過去。這是個 trade-off，不是「越小越好」。

卡點 4：程式送 goal 沒反應，但 rviz2 手動點就會動

原因：八成漏了 waitUntilNav2Active()，或是漏了 use_sim_time。

診斷：

ros2 param get /bt_navigator use_sim_time   # 應為 True（Gazebo 情境）
ros2 action list | grep navigate_to_pose    # 確認 action server 存在
ros2 action info /navigate_to_pose -t

解法：腳本裡 waitUntilNav2Active() 必須在任何 goToPose() 之前。 另外提醒學生：Python 腳本自己也要 use_sim_time，否則它蓋的時間戳是牆鐘時間，Gazebo 的節點會認為這個 goal「來自未來」而丟掉。 可用 ros2 run … --ros-args -p use_sim_time:=true。

卡點 5：ModuleNotFoundError: No module named 'nav2_simple_commander'

診斷：

python3 -c "import nav2_simple_commander; print('ok')"
apt list --installed 2>/dev/null | grep nav2-simple-commander
echo $AMENT_PREFIX_PATH        # 空的 → 根本沒 source

解法：依序 (1) sudo apt install ros-humble-nav2-simple-commander； (2) source /opt/ros/humble/setup.bash；(3) 若在 conda 環境裡跑會找不到系統的 ROS2 套件—— 提醒學生：ROS2 相關程式一律用系統 Python 3.10 跑，不要在 conda 環境裡跑（conda 留給 Day 20 的 Isaac Sim）。 這一條寫進助教手冊的環境章節，因為它會重複發生。
