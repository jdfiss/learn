知識點逐個講解

1. 為什麼要有 Gazebo：模擬器到底在模擬什麼

它解決什麼問題

實體機器人有三個要命的成本：撞壞很貴、每次實驗要重新擺場地很慢、而且「同一件事重跑一百次」幾乎做不到。導航調參、強化學習訓練這種需要大量試錯的工作，在實體機上根本做不完。模擬器把機器人放進一個可以隨時重置、隨時複製、隨時加速的虛擬世界。

白話解釋 + 比喻

Gazebo 做三件事：(a) 算物理——輪子有摩擦力、車有質量、撞到牆會停；(b) 假裝感測器——用射線投射（ray casting）算出「如果這裡有一顆雷射，它會量到多遠」，再包成一個標準 ROS 訊息發出來；(c) 接收指令——收到 /cmd_vel 就真的去轉虛擬輪子。

比喻：Gazebo 像是一間「飛行模擬艙」。艙外的真飛機不存在，但艙內的儀表板（topic）跟真飛機一模一樣。你的 ROS 程式坐在駕駛座上，它完全不知道自己在模擬艙裡——這正是重點：同一份程式碼，換到真機上不用改。這就是為什麼後面 Sim2Real 那一天，我們談的是「差異有多大」，而不是「要不要重寫」。

學生常見誤解

誤解：「Gazebo 是一個 3D 顯示器，跟 RViz 差不多。」
完全不同。Gazebo 是產生資料的地方（模擬真實世界）；RViz 是顯示資料的地方（模擬機器人的腦內畫面）。Gazebo 裡看到的牆是真的存在於物理世界；RViz 裡看到的牆是機器人「以為」有牆。兩邊不一致時，就是機器人認知出錯了——這個區別是之後 Nav2 除錯的核心直覺，今天一定要建立起來。

2. Gazebo Classic 11 vs. 新版 Gazebo（Ignition / Gazebo Sim）

這是初學者最容易在網路教學裡踩到的版本地雷。歷史上 Gazebo 分兩條線：

Gazebo Classic 11Gazebo Sim（舊名 Ignition）
指令gazebo、gzserver、gzclientgz sim（或 ign gazebo）
ROS 橋接套件gazebo_ros_pkgsros_gz_bridge
URDF 內的 plugin 名稱libgazebo_ros_diff_drive.sogz-sim-diff-drive-system
與 Humble 的搭配✅ 本課程鎖定可用但教材少
本課程一律使用 Gazebo Classic 11。如果你 Google 到的文章裡出現 gz sim 或 ros_gz，那是另一條線，plugin 寫法完全不相容，直接跳過那篇。判斷方法：看指令是 gazebo 還是 gz。

3. Gazebo 跟 ROS 是怎麼接起來的：plugin 機制

它解決什麼問題

Gazebo 本身是獨立軟體，它不懂 ROS。那 /scan 是誰發出來的？答案是 plugin（外掛）：一段被載入 Gazebo 行程內部的 C++ 共享函式庫，它一邊讀 Gazebo 的物理狀態，一邊當一個 ROS 2 node 把資料 publish 出去。

白話解釋 + 比喻

plugin 像是「裝在模擬艙儀表板背後的翻譯機」。Gazebo 內部用自己的語言記錄「這台車現在在 (1.2, 0.4)、朝向 30 度」，diff_drive plugin 把它翻譯成 ROS 的 nav_msgs/Odometry 發到 /odom，同時把 /cmd_vel 的 ROS 訊息翻譯回去變成輪子轉速。

你在 URDF/Xacro 裡看到的這種段落，就是在裝翻譯機（TurtleBot3 的 turtlebot3_burger.urdf.xacro 裡就有）：

<!-- URDF 裡的 gazebo 標籤：只有 Gazebo 會讀，rviz2 會忽略 -->
<gazebo>
  <plugin name="turtlebot3_diff_drive"
          filename="libgazebo_ros_diff_drive.so">
    <ros>
      <!-- remapping：plugin 預設發 /odom，這裡可以改名 -->
    </ros>
    <left_joint>wheel_left_joint</left_joint>
    <right_joint>wheel_right_joint</right_joint>
    <wheel_separation>0.160</wheel_separation>   <!-- 兩輪間距 (m) -->
    <wheel_diameter>0.066</wheel_diameter>        <!-- 輪徑 (m) -->
    <odometry_frame>odom</odometry_frame>
    <robot_base_frame>base_footprint</robot_base_frame>
    <publish_odom>true</publish_odom>
    <publish_odom_tf>true</publish_odom_tf>       <!-- 關鍵：這個才會發 odom→base_footprint 的 tf -->
  </plugin>
</gazebo>

學生常見誤解

誤解：「我在 URDF 裡寫了一顆 lidar link，Gazebo 就會發 /scan。」
不會。<link> 只是「一塊有形狀有重量的東西」，把它畫成雷射的樣子不會讓它變成雷射。必須額外加 <gazebo reference="base_scan"><sensor type="ray">...<plugin filename="libgazebo_ros_ray_sensor.so"> 才會真的有資料。「幾何」和「功能」是兩件事——這是 Day 6 URDF 跟今天銜接的關鍵點。

4. /scan：sensor_msgs/LaserScan 逐欄位

這是整個 SLAM 與導航的原料，每個欄位都要能講。

欄位型別物理意義
header.stamptime這一圈掃描的時間戳。tf 要靠它做時間對齊，錯了整個導航就歪
header.frame_idstring這些距離是「以哪個座標系的原點量出來的」，TurtleBot3 是 base_scan
angle_min / angle_maxfloat32 (rad)掃描的起始 / 結束角度。TB3 是 0 到 2π（360 度）
angle_incrementfloat32 (rad)相鄰兩束雷射的夾角。TB3 約 0.0175 rad（1 度）
range_min / range_maxfloat32 (m)感測器可信的距離範圍。超出範圍的值不可以拿來用
ranges[]float32[]核心資料：一整圈的距離陣列，單位公尺
intensities[]float32[]反射強度。多數模擬與便宜雷達是空的或全 0，忽略即可
scan_time / time_incrementfloat32 (s)轉一圈的時間 / 每束之間的時間。高速移動時做去畸變（deskew）才會用到

最重要的一條公式：陣列索引怎麼變成角度。

angle(i) = angle_min + i × angle_increment

逐項解釋：i 是 ranges 陣列的第幾個元素（從 0 開始）；angle_increment 是每往後一格轉多少弧度；算出來的 angle(i) 是相對於 frame_id 那個座標系 +X 軸（機器人正前方）的角度，逆時針為正（ROS 統一右手座標系：X 前、Y 左、Z 上）。反過來，如果你想知道「正前方的距離」，就是 i = 0（因為 angle_min = 0 且正前方就是 0 度）；「正左方 90 度」就是 i = 90；「正右方」是 i = 270。

學生常見誤解

誤解：「min(msg.ranges) 就是最近障礙物的距離。」
會炸。ranges 裡通常混著 inf（那個方向什麼都沒打到）和 0.0 或 nan（無效讀值）。min() 很可能回傳 0.0，讓你的程式以為「前面貼著一面牆」而永遠停住。正確做法是先過濾：只留下 range_min < r < range_max 且 math.isfinite(r) 的值。這是助教會被問到爛的第一名問題。

5. /odom：nav_msgs/Odometry 與「里程計會漂」

它解決什麼問題

機器人要知道「我從出發點走到哪了」。最便宜的方法是數輪子轉了幾圈，再用幾何積分推算位置——這就是輪式里程計（wheel odometry）。

結構

nav_msgs/Odometry
  header.stamp                 # 時間
  header.frame_id   = "odom"           # 這個位姿是在 odom 座標系裡表達的
  child_frame_id    = "base_footprint" # 被描述的對象是誰
  pose.pose.position.{x,y,z}           # 位置 (m)
  pose.pose.orientation.{x,y,z,w}      # 姿態，四元數（Day 5 學過）
  pose.covariance[36]                  # 6x6 共變異數，代表「我對這個估計有多不確定」
  twist.twist.linear.{x,y,z}           # 速度 (m/s)，在 child_frame 裡表達
  twist.twist.angular.{x,y,z}          # 角速度 (rad/s)
  twist.covariance[36]

白話解釋 + 比喻

frame_id 和 child_frame_id 這組搭配的意思是：「base_footprint 這個東西，在 odom 這個座標系裡，位在哪、朝哪」。比喻：你閉著眼睛從家門口走出去，每一步都默數「往前 70 公分、左轉 30 度」。你算出來的位置就是 odometry。它短時間內非常準、非常平滑（不會突然跳），但誤差只會累積不會修正——走一百步之後你可能差了兩公尺，而且你自己不知道。

這就是為什麼之後 Nav2 要有 map → odom 這一層：AMCL 用雷射比對地圖，算出「你以為的位置」和「真實位置」的偏差，把它塞進 map→odom 這個轉換裡去修正。odom 負責平滑、map 負責正確，兩層分工——Day 10 你會再遇到這句話。

學生常見誤解

誤解：「Gazebo 裡的 /odom 是完美的真值（ground truth），所以模擬沒有漂移問題。」
不一定。libgazebo_ros_diff_drive.so 預設是從關節角度積分算出來的，只要輪子打滑（撞牆、加速過猛）就會漂，跟真機同一個病。真正的真值要另外用 libgazebo_ros_p3d.so（ground truth plugin）才拿得到。所以在 Gazebo 裡練習「處理里程計漂移」是有意義的。

6. /cmd_vel：geometry_msgs/Twist 與差動輪的限制

結構極簡，只有兩個 3D 向量：

geometry_msgs/Twist
  linear.x   # 前進速度 m/s（正=前進，負=倒車）
  linear.y   # 側移速度 —— 差動輪機器人「永遠是 0」
  linear.z   # 垂直 —— 地面機器人永遠 0
  angular.x  # roll  —— 地面機器人永遠 0
  angular.y  # pitch —— 地面機器人永遠 0
  angular.z  # yaw 角速度 rad/s（正=左轉/逆時針）

為什麼 linear.y 必須是 0？這叫非完整約束（nonholonomic constraint）。白話：兩顆輪子只能往前後滾，不能橫著滑，所以車子沒有辦法「原地向左平移」——就像汽車不能橫著開進停車格，只能靠倒車入庫這種「繞路」的方式達成。麥克納姆輪（mecanum）或全向輪機器人才能用 linear.y。

plugin 內部會把 Twist 換算成左右輪速度：

v_left = linear.x − angular.z × (L / 2)
v_right = linear.x + angular.z × (L / 2)

其中 L 是 wheel_separation（兩輪中心距離，TB3 burger 是 0.160 m）。看這條式子就懂了：angular.z 是靠「左右輪速度差」造出來的；linear.x = 0 而 angular.z ≠ 0 時，左右輪一正一反，就是原地自轉。

學生常見誤解

誤解：「我發一次 /cmd_vel，機器人就會一直走。」
在模擬裡確實會一直走（plugin 記住最後一個指令），但這是危險的習慣。實機的驅動器普遍有 watchdog：超過 0.2～0.5 秒沒收到新指令就自動煞停，避免程式當掉後機器人衝出去。所以正確寫法是用 timer 以固定頻率（10～20 Hz）持續發布，而不是發一次就走人。Day 24 講實機安全時會再強調一次。

7. /tf 與 /tf_static：模擬中誰在發什麼

Day 5 你學過 tf2 的原理，今天要落到「實際上有哪些節點在餵資料」。跑起 TurtleBot3 模擬後，tf tree 長這樣：

odom ──(diff_drive plugin，動態，~30Hz)──> base_footprint
base_footprint ──(robot_state_publisher，靜態)──> base_link
base_link ──(robot_state_publisher，靜態)──> base_scan / imu_link / caster
base_link ──(robot_state_publisher，由 /joint_states 驅動)──> wheel_left_link / wheel_right_link

要記住的分工：

  • diff_drive plugin 發 odom → base_footprint。這是唯一會隨機器人移動而改變的那一段。
  • robot_state_publisher 讀 URDF，把所有 fixed joint 一次發到 /tf_static（只發一次，用 TRANSIENT_LOCAL QoS 讓晚加入的節點也收得到），把 continuous/revolute joint 依 /joint_states 持續發到 /tf。
  • 目前還沒有 map frame。Day 9 開 slam_toolbox、Day 10 開 AMCL 之後才會補上 map → odom。今天如果 RViz 裡把 Fixed Frame 設成 map 會整片報錯，這是正常的，設成 odom 就好。

8. 模擬時間 use_sim_time：今天最大的坑

它解決什麼問題

Gazebo 的物理計算不一定跟真實時間同速——GPU 慢的時候可能只跑 0.6 倍速。如果你的節點用電腦時鐘（wall clock）打時間戳，Gazebo 用模擬時鐘，兩邊時間軸就對不上，tf 查詢會不斷失敗。

白話解釋 + 比喻

Gazebo 會在 /clock 這個 topic 上廣播「模擬世界現在幾點」。當一個節點設定 use_sim_time:=true，它就不看自己的手錶，改看牆上那面公用時鐘。比喻：整個劇組拍片時都看場記的碼表，不看自己的手機，這樣剪接才對得起來。只要有一個人看自己手機，他那段畫面就永遠對不上。

規則：只要 Gazebo 在跑，你啟動的每一個節點都要開 sim time，一個都不能漏。

# 用 CLI 跑節點時
ros2 run my_pkg my_node --ros-args -p use_sim_time:=true

# rviz2 也要
ros2 run rviz2 rviz2 --ros-args -p use_sim_time:=true

學生常見誤解

誤解：「Lookup would require extrapolation into the past 是 tf 設定寫錯了。」
九成不是。這行錯誤最常見的原因就是某個節點忘了開 use_sim_time：它用 2026 年的真實時間去查一個「開機才 30 秒」的模擬時間軸，當然查不到。看到這個錯誤，第一個動作是 ros2 param get /那個節點 use_sim_time，不是去改 tf。

9. QoS 不匹配：訂閱了 /scan 卻一筆資料都收不到

它解決什麼問題

Day 2 學過 QoS。今天是第一次真正被它咬。感測器資料的特性是「量大、頻繁、丟一兩筆沒關係，但寧可丟也不要延遲」，所以 ROS 2 定義了 rclpy.qos.qos_profile_sensor_data：Reliability = BEST_EFFORT、Depth = 5。Gazebo 的 ray sensor plugin 就是用這個 profile 發 /scan。

白話解釋 + 比喻

而 create_subscription 如果你只填一個數字當 QoS（例如 10），拿到的是預設 profile：RELIABLE。DDS 的相容規則是「訂閱端不能要求比發布端更強的保證」——publisher 說「我盡力送，不保證」，subscriber 說「我要求每筆必到」，談不攏，連線根本不會建立。

比喻：寄件人只肯用平信，收件人堅持要掛號回執。郵局的規定是談不攏就不收件——所以不是「信寄丟了」，而是從頭到尾一封都沒寄出。這就是為什麼症狀是「callback 完全沒被呼叫過」，而不是「偶爾漏收」。

診斷指令：ros2 topic info /scan --verbose，看 Publisher 和 Subscriber 兩邊的 Reliability 是不是一樣。ros2 topic echo /scan 看得到、但你的 node 收不到 → 幾乎必然是 QoS（echo 會自動適配，你的程式不會）。

可直接複製貼上的指令與程式碼

A. 安裝 TurtleBot3 模擬環境

# ---- 1. 安裝 TurtleBot3 與 Gazebo 相關套件（apt 版，最省事）----
sudo apt update
sudo apt install -y \
  ros-humble-turtlebot3 \
  ros-humble-turtlebot3-msgs \
  ros-humble-turtlebot3-simulations \
  ros-humble-gazebo-ros-pkgs \
  ros-humble-tf2-tools \
  ros-humble-rqt-graph \
  ros-humble-rqt-tf-tree

# ---- 2. 設定環境變數（每開一個新 terminal 都要，所以寫進 .bashrc）----
echo "source /opt/ros/humble/setup.bash"            >> ~/.bashrc
echo "export TURTLEBOT3_MODEL=burger"               >> ~/.bashrc
echo "export ROS_DOMAIN_ID=30"                      >> ~/.bashrc   # 同網段避免互相干擾
# Gazebo 要找得到 TB3 的模型檔，否則世界會缺物件
echo "export GAZEBO_MODEL_PATH=\$GAZEBO_MODEL_PATH:/opt/ros/humble/share/turtlebot3_gazebo/models" >> ~/.bashrc
source ~/.bashrc

# ---- 3. 驗證 ----
echo $TURTLEBOT3_MODEL      # 應該印出 burger
gazebo --version | head -1  # 應該是 11.x

B. 啟動世界並操控

ros2 launch turtlebot3_gazebo turtlebot3_world.launch.py

# === Terminal 2：鍵盤遙控（w/x 加減速、a/d 轉向、s 或空白鍵停止）===

# === Terminal 3：RViz 觀察（注意 Fixed Frame 要設 odom，今天還沒有 map）===
ros2 launch turtlebot3_bringup rviz2.launch.py

C. 用 CLI 解剖四個 topic（今天的核心練習）

# ---- 先看全景 ----
ros2 topic list -t                 # -t 會一併列出訊息型別
ros2 node list
rqt_graph                          # 圖形化：誰發給誰

# ---- /scan：先看型別定義，再看實際資料 ----
ros2 interface show sensor_msgs/msg/LaserScan
ros2 topic hz /scan                            # 頻率，TB3 約 5 Hz
ros2 topic info /scan --verbose                # ★ 看 QoS，注意 Reliability=BEST_EFFORT
# 只印 header 跟角度參數，不要被 360 筆 ranges 洗版
ros2 topic echo /scan --field angle_increment --once
ros2 topic echo /scan --field range_max --once
# 印出正前方那一束（index 0）
ros2 topic echo /scan --field ranges[0]

# ---- /odom ----
ros2 topic echo /odom --field pose.pose.position --once
ros2 topic echo /odom --field twist.twist --once
ros2 topic echo /odom --field child_frame_id --once   # base_footprint

# ---- /cmd_vel：從命令列直接開車（-r 2 = 以 2Hz 重複發，符合 watchdog 習慣）----
ros2 topic pub -r 2 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.1, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.5}}"

ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.0}}"

D. 今日程式：LaserScan 避障節點

建在 Day 3 做好的 workspace 裡。三個重點：sensor_data QoS、過濾 inf/nan、用 timer 固定頻率發 cmd_vel。

# ~/ros2_ws/src/tb3_play/tb3_play/obstacle_stop.py
#!/usr/bin/env python3
import math
import rclpy
from rclpy.node import Node
from rclpy.qos import qos_profile_sensor_data      # ★ 關鍵：BEST_EFFORT
from sensor_msgs.msg import LaserScan
from geometry_msgs.msg import Twist


class ObstacleStop(Node):
    def __init__(self):
        super().__init__('obstacle_stop')

        # 參數化，方便之後用 ros2 param set 即時調整
        self.declare_parameter('stop_distance', 0.35)   # 公尺
        self.declare_parameter('forward_speed', 0.15)   # m/s
        self.declare_parameter('cone_deg', 20)          # 正前方 ±20 度算「前方」

        # ★ 用 qos_profile_sensor_data，否則 callback 一次都不會被呼叫
        self.sub = self.create_subscription(
            LaserScan, '/scan', self.scan_cb, qos_profile_sensor_data)
        self.pub = self.create_publisher(Twist, '/cmd_vel', 10)

        # ★ 固定 10Hz 發布，模擬實機 watchdog 的正確習慣
        self.timer = self.create_timer(0.1, self.tick)

        self.front_dist = float('inf')
        self.got_scan = False
        self.get_logger().info('obstacle_stop 啟動，等待 /scan ...')

    def scan_cb(self, msg: LaserScan):
        if not self.got_scan:
            self.got_scan = True
            self.get_logger().info(
                f'收到第一筆 scan：{len(msg.ranges)} 束, '
                f'angle_min={msg.angle_min:.3f}, inc={msg.angle_increment:.4f}')

        cone = math.radians(self.get_parameter('cone_deg').value)
        valid = []
        for i, r in enumerate(msg.ranges):
            # ★ 三重過濾：非有限值、超出感測器可信範圍，一律丟掉
            if not math.isfinite(r):
                continue
            if r < msg.range_min or r > msg.range_max:
                continue
            # index -> 角度，再正規化到 (-pi, pi] 方便判斷「前方」
            ang = msg.angle_min + i * msg.angle_increment
            ang = math.atan2(math.sin(ang), math.cos(ang))
            if abs(ang) <= cone:
                valid.append(r)

        # 前方沒有任何有效讀值 = 空曠，視為無限遠（不是 0！）
        self.front_dist = min(valid) if valid else float('inf')

    def tick(self):
        cmd = Twist()
        if not self.got_scan:
            self.pub.publish(cmd)          # 還沒資料就保持靜止
            return

        stop_d = self.get_parameter('stop_distance').value
        speed = self.get_parameter('forward_speed').value

        if self.front_dist > stop_d:
            cmd.linear.x = speed
            cmd.angular.z = 0.0
        else:
            cmd.linear.x = 0.0
            cmd.angular.z = 0.5            # 停下來並原地左轉找路
            self.get_logger().warn(
                f'前方 {self.front_dist:.2f} m，煞車並轉向', throttle_duration_sec=1.0)

        self.pub.publish(cmd)

    def on_shutdown(self):
        self.pub.publish(Twist())          # ★ 離開前一定要送一筆全 0


def main():
    rclpy.init()
    node = ObstacleStop()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.on_shutdown()
        node.destroy_node()
        rclpy.shutdown()


if __name__ == '__main__':
    main()
# ---- 註冊進 setup.py 的 entry_points ----

🎓 助教筆記：學生最常卡住的 5 個問題

卡點 1：Gazebo 開起來是全黑 / 卡在 white screen / 直接閃退

錯誤訊息：[gzclient] VMware: vmw_ioctl_command error Invalid argument. 或 [Err] [REST.cc:205] Error in REST request，或者完全沒訊息就退出。

診斷指令：

echo $DISPLAY                      # 空的 = 沒有 X11，例如 SSH 沒開 -X
glxinfo | grep "OpenGL renderer"   # 應顯示 NVIDIA；顯示 llvmpipe 代表在用軟體渲染
nvidia-smi                         # 確認驅動有載入
ps aux | grep gz                   # 看有沒有殘留的 gzserver

解法：

  • REST 那個 Err 是要連 Gazebo 模型網站失敗，純警告，不影響——先讓學生別慌。改 ~/.ignition/fuel/config.yaml 的 url 可消除。
  • 虛擬機 / 遠端桌面環境跑不動 3D：export SVGA_VGPU10=0，或改用無畫面模式 gzserver only（launch 加 gui:=false），資料照樣有，只是看不到畫面。
  • 顯示 llvmpipe 代表沒吃到 NVIDIA：檢查 prime-select nvidia 後重開機。
  • 第一次啟動就是會慢 30～90 秒（下載模型 + 編譯 shader），叫學生等，不要一直 Ctrl+C 重來。

卡點 2：[Err] [Model.cc] Missing model: turtlebot3_burger / 世界是空的沒有機器人

根因：九成是 TURTLEBOT3_MODEL 沒設，或設在別的 terminal。剩下一成是 GAZEBO_MODEL_PATH 沒包含 turtlebot3_gazebo/models。

echo $TURTLEBOT3_MODEL             # 空的就是元兇
echo $GAZEBO_MODEL_PATH
export TURTLEBOT3_MODEL=burger     # 立即修
助教話術：「環境變數只活在那一個 terminal 裡。你剛剛 export 的那個視窗有效，新開的視窗沒有。要每個視窗都有，就寫進 ~/.bashrc。」——這個觀念一天會被問五次，準備好一句話版本。

卡點 3：訂閱 /scan 但 callback 從來沒被呼叫（最高頻、最難自己發現）

症狀：程式不報錯、不當掉，就是安安靜靜什麼都沒發生。學生會以為是自己 spin() 寫錯。

診斷 SOP：

ros2 topic echo /scan               # 有資料 → 排除「感測器沒發」
ros2 node info /你的節點名           # 確認 subscription 真的建立了
ros2 topic info /scan --verbose     # ★ 對照兩邊的 Reliability

看到這樣就是中獎：

Publisher: ... Reliability: BEST_EFFORT
Subscription: ... Reliability: RELIABLE      ← 談不攏，連線不成立

解法：訂閱端改用 qos_profile_sensor_data。順便教學生記口訣：「感測器資料一律 sensor_data QoS，指令與狀態才用預設 reliable。」

卡點 4：Lookup would require extrapolation into the past/future 或 RViz 一直閃紅字

錯誤訊息全文範例：[tf2_ros] Lookup would require extrapolation into the past. Requested time 1799.3 but the earliest data is at time 1802.1, when looking up transform from frame [base_scan] to frame [odom]

診斷順序（照這個順序問，不要跳）：

# 1. 這個節點有沒有開 sim time？（八成的答案在這裡）
ros2 param get /你的節點 use_sim_time
ros2 param get /rviz2 use_sim_time

# 2. /clock 有在發嗎？
ros2 topic hz /clock

# 3. tf 到底有沒有斷層？
ros2 run tf2_ros tf2_echo odom base_scan
ros2 run tf2_tools view_frames && xdg-open frames.pdf

解法：所有節點（含 rviz2）加 --ros-args -p use_sim_time:=true。若是自己寫的 launch 檔，記得每個 Node 都要帶 parameters=[{'use_sim_time': True}]——漏掉其中一個就會出現這個錯。

卡點 5：Ctrl+C 之後重開 Gazebo 就壞掉 / port 被佔 / 機器人自己還在動

錯誤訊息：[Err] [Master.cc:96] EXCEPTION: Unable to start server[bind: Address already in use]

根因：gzserver 是背景行程，Ctrl+C 常常只殺掉 launch，server 還活著佔用 11345 port。

# 標準清場三連（叫學生設成 alias，一天要用十次）
pkill -9 gzserver ; pkill -9 gzclient ; pkill -9 rviz2
sleep 2
ros2 daemon stop && ros2 daemon start     # ROS 2 的 discovery 快取也清一下

另外提醒：teleop 或 topic pub -r 關掉後，plugin 記得的是最後一筆非零指令，車子會繼續跑。教學生養成習慣：結束前一定補一筆全 0 的 /cmd_vel。這在模擬只是煩，在實機是安全事故。

額外一則，明天會用到：如果學生問「為什麼 RViz 裡機器人是白色/沒有材質」，那是 URDF 的 <material> 在 Gazebo 與 RViz 使用不同的定義方式（RViz 讀 URDF material，Gazebo 讀 <gazebo><material>Gazebo/DarkGrey</material>）。純外觀問題，不影響功能，可以先放著。
