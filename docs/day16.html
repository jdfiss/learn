一、Planning Scene：機器人「腦中的世界」

它解決什麼問題

Day 15 你讓 MoveIt2 規劃了一條軌跡，但那時候世界是空的——機器人只避開了自己的手臂（自碰撞）。真實情境裡桌子、箱子、要抓的物件都在那，規劃器必須知道它們存在，否則規劃出來的路徑會直接穿過桌面。

Planning Scene 就是 move_group 節點內部維護的那份「世界快照」，內容包含三件事：

  1. 機器人目前狀態（每個關節的角度，從 /joint_states 來）
  2. 世界裡的碰撞物件（桌子、方塊、牆，還有從深度相機來的 octomap）
  3. ACM（Allowed Collision Matrix）：哪些「碰撞」是被允許、可以忽略的
比喻：Planning Scene 就像你閉著眼睛在自己房間走路時腦中的那張地圖。你知道床在左邊、櫃子在右邊，所以能繞開。如果有人趁你睡覺搬了一張椅子到中間而你不知道——你腦中的地圖沒更新——你就會撞上去。MoveIt2 完全一樣：它只會避開它「知道」的東西。Gazebo 裡看得到不代表 MoveIt2 知道；那是兩份互不相通的世界。
學生常見誤解：「我在 Gazebo 裡放了一張桌子，MoveIt2 應該就會避開它。」
不會。Gazebo 是物理模擬器，MoveIt2 是規劃器，兩者各有各的世界模型。除非你（a）自己把 CollisionObject 加進 Planning Scene，或（b）接上深度相機讓 occupancy_map_monitor 產生 octomap，否則 MoveIt2 眼中桌子不存在。規劃出來會穿過去，然後在 Gazebo 裡撞爛。

怎麼改 Planning Scene：兩條路，選對很重要

方式介面特性
Topic/collision_object（moveit_msgs/CollisionObject）fire-and-forget，發了不知道有沒有生效。最常見的坑：publisher 剛建立、move_group 還沒訂閱到就發出去，訊息直接掉了
Service/apply_planning_scene（moveit_msgs/srv/ApplyPlanningScene）同步、有回傳值，確定生效才往下走。寫腳本一律用這個

CollisionObject 的三種幾何

  • Primitive（BOX / SPHERE / CYLINDER / CONE）：碰撞檢查最快，桌子、方塊、柱子都用這個。預設就該用它。
  • Mesh（.stl / .dae）：形狀精確，但碰撞檢查慢很多（FCL 要跑三角面片對三角面片）。真的需要才用，而且要簡化面數。
  • Plane：無限大平面，偶爾拿來當地板。

operation 欄位決定動作：ADD（新增／覆蓋同 id 的物件）、REMOVE（刪除）、MOVE（只改位姿，不重建幾何）。id 是唯一鍵，同 id 再 ADD 一次就是覆蓋。

ACM：為什麼「允許碰撞」是必要的而不是作弊

夾爪的兩根手指要夾住方塊，就必然會跟方塊碰撞。如果碰撞檢查器嚴格執行「任何接觸都是碰撞」，那抓取這件事在數學上永遠規劃不出來。ACM 就是一張表，記錄「這對物體之間的接觸請忽略」。

URDF 載入時 MoveIt Setup Assistant 已經幫你把「永遠不可能碰到」和「相鄰連桿本來就相接」的組合寫進 SRDF 的 <disable_collisions>，那些就是初始 ACM。你在程式裡 attach 物件時指定的 touch_links，就是動態往 ACM 加項目。

二、attach / detach：不只是視覺效果

它解決什麼問題

夾爪閉合、方塊被夾住了。此時如果你直接叫 MoveIt2 規劃移動，會發生兩件壞事：

  1. 方塊還被當成「世界中的靜止障礙物」，而它現在就貼在夾爪上 → 規劃器認為機器人正處於碰撞狀態，直接回 Start state is in collision，什麼都規劃不出來。
  2. 就算硬繞過去，規劃器不知道手上多了一個 5 公分的方塊，會規劃出讓方塊掃過桌邊的路徑 → 實機上把東西撞飛。

attach 做的事：把物件從「世界」搬到「機器人身上」，變成 AttachedCollisionObject，掛在指定的 link（通常是夾爪的 hand 或 tool0）上，跟著那個 link 一起動。從此規劃器把它當成機器人的一部分來做碰撞檢查。

比喻：你手上端著一杯滿的咖啡走過窄門。你的大腦會自動把「杯子」納入身體範圍，肩膀轉的角度會不一樣。attach 就是告訴機器人「這杯咖啡現在算你身體的一部分」。沒 attach 的機器人，就像忘了自己手上有杯子的人——直直走進門框，咖啡撒一地。
touch_links 是新手第一個大坑。attach 之後，物件跟夾爪手指必然接觸。如果你沒有在 touch_links 裡列出夾爪的所有手指 link，碰撞檢查器會判定「機器人自己撞到自己身上掛的東西」→ 一樣規劃失敗。touch_links 要填的是被允許跟這個物件接觸的 link 名稱清單，通常是整個夾爪群組的所有 link。
學生常見誤解：「attach 之後，Gazebo 裡的方塊就會跟著手臂走。」
不會。attach 只改變 MoveIt2 的碰撞模型與 rviz 的顯示。物理上方塊會不會跟著走，取決於 Gazebo 裡夾爪的摩擦力參數夠不夠、以及有沒有掛 gazebo_ros_link_attacher 之類的插件。模擬中方塊從指縫滑掉是常態，那是物理引擎的問題，不是 MoveIt2 的問題——診斷時要先分清楚是哪一邊。

三、Cartesian path：為什麼「抬起來」不能用一般規劃

它解決什麼問題

OMPL 這類取樣式規劃器（RRT-Connect 等）只保證「起點到終點、不撞到東西」，中間路徑長什麼樣完全隨機。對「從 A 點移動到 B 點」沒問題，但對兩個動作是災難：

  • approach（伸進去抓）：夾爪必須沿著抓取方向直線靠近，不然會從側面撞倒物件。
  • retreat（抓完抬起）：必須垂直向上直線提，OMPL 可能規劃出一條先橫向甩再上升的路徑，物件直接刮到桌面。

Cartesian path 是在笛卡兒空間（末端點的 x,y,z + 姿態）做直線插值，把直線切成很多小段，每一段用 IK 解出關節角。介面是 /compute_cartesian_path 服務（moveit_msgs/srv/GetCartesianPath）。

三個關鍵參數

fraction = 成功走完的路徑長度 ÷ 你要求的總路徑長度
參數物理意義建議值
max_step（eef_step）末端每一小步走多遠（公尺）。太大 → 插值太粗，中間可能穿過障礙；太小 → IK 要解幾千次，很慢0.01（1 公分）
jump_threshold相鄰兩點的關節角容許跳多少。設 0.0 代表完全關閉檢查——實機上這會讓手臂在經過奇異點時瞬間甩動，非常危險模擬 0.0 可接受；實機請設 5.0 左右
回傳的 fraction1.0 = 整段直線都走得到；0.4 = 只走到 40% 就卡住（撞到東西、超出工作空間、或 IK 無解）< 0.9 就不要執行，先查原因
學生常見誤解：「fraction 回 0.6，那就執行那 60% 吧，總比不動好。」
非常危險。fraction 0.6 代表手臂會走到半路然後停在一個你沒預期的位置——可能夾爪還沒到物件上方就停了，接著程式往下執行「關夾爪」，夾住空氣或撞到桌面。正確做法是把 fraction 當成 assert：不到 0.9 就 raise，印出目前 pose 與目標 pose 的差距去查。

#步驟用什麼規劃失敗時最可能的原因
1Pre-grasp：移到物件正上方 10 cm，夾爪朝下、張開OMPL（一般規劃）IK 無解（姿態不可達）、起始狀態碰撞

6Place + Detach：移到放置點、下降、開夾爪、detach、退開OMPL + Cartesiandetach 後物件留在舊位置（要 MOVE 到新位置或直接 REMOVE）
💡 為什麼不用 MoveIt Task Constructor (MTC)？
MTC 是官方推薦的 pick&place 框架，它把上面六步變成可組合的 stage，還會自動嘗試多個 grasp 候選。但它是 C++ 為主、概念也重。今天先用手寫六步把每一步的失敗模式摸熟——之後學生問「MTC 為什麼規劃不出來」，你才有能力拆開來看是哪一個 stage 死掉。Day 21 整合專題時可以再回頭評估要不要導入 MTC。

5-3 Python：用 service 安全地加入碰撞物件

#!/usr/bin/env python3
"""scene_helper.py — 用 /apply_planning_scene 服務同步操作 Planning Scene。
比 topic 可靠：呼叫回來就保證 move_group 已經吃進去了。"""

import rclpy
from rclpy.node import Node
from moveit_msgs.srv import ApplyPlanningScene
from moveit_msgs.msg import (PlanningScene, CollisionObject,
                             AttachedCollisionObject)
from shape_msgs.msg import SolidPrimitive
from geometry_msgs.msg import Pose


class SceneHelper(Node):
    def __init__(self, planning_frame="panda_link0"):
        super().__init__("scene_helper")
        self.frame = planning_frame
        self.cli = self.create_client(ApplyPlanningScene, "/apply_planning_scene")
        # 一定要等服務起來，不然 call 出去石沉大海
        while not self.cli.wait_for_service(timeout_sec=2.0):
            self.get_logger().info("等待 /apply_planning_scene ...")

    def _apply(self, scene: PlanningScene) -> bool:
        # is_diff=True 代表「這是增量修改」，不是整份覆蓋。
        # 忘記設 True 會把整個場景清空，只剩你這次送的東西 —— 很常見的坑
        scene.is_diff = True
        req = ApplyPlanningScene.Request()
        req.scene = scene
        fut = self.cli.call_async(req)
        rclpy.spin_until_future_complete(self, fut, timeout_sec=5.0)
        ok = fut.result() is not None and fut.result().success
        self.get_logger().info(f"apply_planning_scene -> {ok}")
        return ok

    def add_box(self, obj_id, size_xyz, pos_xyz):
        """加一個長方體。size_xyz / pos_xyz 都是 (x, y, z)，單位公尺。"""
        co = CollisionObject()
        co.header.frame_id = self.frame
        co.id = obj_id

        box = SolidPrimitive()
        box.type = SolidPrimitive.BOX
        box.dimensions = list(size_xyz)

        pose = Pose()
        pose.position.x, pose.position.y, pose.position.z = pos_xyz
        pose.orientation.w = 1.0   # 單位四元數；忘了設 w=1 會得到 (0,0,0,0) 非法四元數

        co.primitives = [box]
        co.primitive_poses = [pose]
        co.operation = CollisionObject.ADD

        scene = PlanningScene()
        scene.world.collision_objects = [co]
        return self._apply(scene)

    def remove(self, obj_id):
        co = CollisionObject()
        co.header.frame_id = self.frame
        co.id = obj_id
        co.operation = CollisionObject.REMOVE
        scene = PlanningScene()
        scene.world.collision_objects = [co]
        return self._apply(scene)

    def attach(self, obj_id, link="panda_hand", touch_links=None):
        """把世界中的物件掛到 link 上。
        touch_links：允許跟這個物件接觸的 link 清單 —— 沒填全就規劃不出來。"""
        if touch_links is None:
            touch_links = ["panda_hand", "panda_leftfinger", "panda_rightfinger",
                           "panda_hand_tcp"]
        aco = AttachedCollisionObject()
        aco.link_name = link
        aco.object.id = obj_id
        aco.object.operation = CollisionObject.ADD
        aco.touch_links = touch_links

        scene = PlanningScene()
        scene.robot_state.attached_collision_objects = [aco]
        scene.robot_state.is_diff = True     # robot_state 也要標 is_diff
        return self._apply(scene)

    def detach(self, obj_id, link="panda_hand"):
        aco = AttachedCollisionObject()
        aco.link_name = link
        aco.object.id = obj_id
        aco.object.operation = CollisionObject.REMOVE
        scene = PlanningScene()
        scene.robot_state.attached_collision_objects = [aco]
        scene.robot_state.is_diff = True
        return self._apply(scene)


if __name__ == "__main__":
    rclpy.init()
    h = SceneHelper()
    h.add_box("table", (0.4, 0.6, 0.02), (0.5, 0.0, 0.20))
    h.add_box("cube",  (0.04, 0.04, 0.04), (0.5, 0.0, 0.23))
    h.get_logger().info("場景已建立，去 rviz 看看")
    rclpy.shutdown()

5-4 Python：Cartesian path（用服務，最穩的寫法）

#!/usr/bin/env python3
"""cartesian_helper.py — 呼叫 /compute_cartesian_path 做直線移動。
moveit_py 的 Cartesian API 在不同版本之間有變動，直接打服務最保險，
而且看得到底層在傳什麼，除錯容易很多。"""

import copy
import rclpy
from rclpy.node import Node
from moveit_msgs.srv import GetCartesianPath
from geometry_msgs.msg import Pose


class CartesianHelper(Node):
    def __init__(self, group="panda_arm", eef_link="panda_hand_tcp",
                 frame="panda_link0"):
        super().__init__("cartesian_helper")
        self.group, self.eef, self.frame = group, eef_link, frame
        self.cli = self.create_client(GetCartesianPath, "/compute_cartesian_path")
        while not self.cli.wait_for_service(timeout_sec=2.0):
            self.get_logger().info("等待 /compute_cartesian_path ...")

    def straight_line(self, start_pose: Pose, dxyz, min_fraction=0.9):
        """從 start_pose 沿 dxyz=(dx,dy,dz) 走直線。回傳 (trajectory, fraction)。"""
        target = copy.deepcopy(start_pose)
        target.position.x += dxyz[0]
        target.position.y += dxyz[1]
        target.position.z += dxyz[2]

        req = GetCartesianPath.Request()
        req.header.frame_id = self.frame
        req.group_name = self.group
        req.link_name = self.eef
        req.waypoints = [target]
        req.max_step = 0.01          # 每 1 cm 插一個點
        req.jump_threshold = 0.0     # 模擬可用 0.0；實機請改 5.0
        req.avoid_collisions = True

        fut = self.cli.call_async(req)
        rclpy.spin_until_future_complete(self, fut, timeout_sec=10.0)
        res = fut.result()
        if res is None:
            raise RuntimeError("compute_cartesian_path 沒有回應")

        frac = res.fraction
        self.get_logger().info(f"Cartesian fraction = {frac:.3f}")
        if frac < min_fraction:
            # 把 fraction 當 assert，不要執行半條路徑
            raise RuntimeError(
                f"直線只走得到 {frac*100:.0f}%。檢查：(1) 途中有沒有碰撞物件 "
                f"(2) 目標超出工作空間 (3) 經過奇異點 "
                f"(4) 該 attach 的物件忘了 attach")
        return res.solution, frac

5-5 主程式：Pick & Place 六步骨架

#!/usr/bin/env python3
"""pick_place.py — Pick & Place 六步。
執行方式（重要）：MoveItPy 需要完整的 robot_description / kinematics 參數，
不能直接 python3 跑，要透過 launch 檔用 MoveItConfigsBuilder 帶參數進來。
最快的做法是複製 moveit2_tutorials 的 motion_planning_python_api_tutorial.launch.py
把裡面指向的 python 檔改成這一支。"""

import time
import rclpy
from moveit.planning import MoveItPy
from geometry_msgs.msg import Pose, PoseStamped

from scene_helper import SceneHelper
from cartesian_helper import CartesianHelper

FRAME = "panda_link0"
CUBE_POS = (0.45, 0.0, 0.23)      # 方塊中心
PLACE_POS = (0.45, 0.30, 0.23)    # 放置點


def make_grasp_pose(x, y, z):
    """夾爪朝下的抓取姿態。
    (x,y,z,w)=(1,0,0,0) 代表繞 X 軸轉 180 度 —— 也就是 Z 軸從朝上翻成朝下。
    這一步的四元數是新手最容易搞錯的地方，Day 5 的 quaternion 概念要拿出來用。"""
    p = Pose()
    p.position.x, p.position.y, p.position.z = x, y, z
    p.orientation.x, p.orientation.y = 1.0, 0.0
    p.orientation.z, p.orientation.w = 0.0, 0.0
    return p


def plan_and_execute(robot, component, logger, sleep_time=0.5):
    """一般規劃（OMPL）+ 執行。"""
    plan_result = component.plan()
    if not plan_result:
        raise RuntimeError("規劃失敗：檢查目標是否可達、起始狀態是否碰撞")
    robot.execute(plan_result.trajectory, controllers=[])
    time.sleep(sleep_time)


def main():
    rclpy.init()

    # --- 步驟 0：建立場景 ---
    scene = SceneHelper(FRAME)
    scene.add_box("table", (0.4, 0.6, 0.02), (0.5, 0.0, 0.20))
    scene.add_box("cube",  (0.04, 0.04, 0.04), CUBE_POS)

    robot = MoveItPy(node_name="pick_place_py")
    arm = robot.get_planning_component("panda_arm")
    hand = robot.get_planning_component("hand")
    logger = robot.get_logger()
    cart = CartesianHelper("panda_arm", "panda_hand_tcp", FRAME)

    # --- 步驟 1：Pre-grasp，移到方塊正上方 10 cm ---
    logger.info("[1/6] pre-grasp")
    pre = PoseStamped()
    pre.header.frame_id = FRAME
    pre.pose = make_grasp_pose(CUBE_POS[0], CUBE_POS[1], CUBE_POS[2] + 0.12)
    arm.set_start_state_to_current_state()
    arm.set_goal_state(pose_stamped_msg=pre, pose_link="panda_hand_tcp")
    plan_and_execute(robot, arm, logger)

    # --- 步驟 2：Approach，直線下降到抓取位姿 ---
    logger.info("[2/6] approach（Cartesian 直線下降）")
    traj, frac = cart.straight_line(pre.pose, (0.0, 0.0, -0.10))
    robot.execute(traj, controllers=[])

    # --- 步驟 3：關夾爪 ---
    logger.info("[3/6] 關夾爪")
    hand.set_start_state_to_current_state()
    hand.set_goal_state(configuration_name="close")   # SRDF 裡定義的 named state
    plan_and_execute(robot, hand, logger)

    # --- 步驟 4：Attach ---
    logger.info("[4/6] attach cube")
    scene.attach("cube", link="panda_hand",
                 touch_links=["panda_hand", "panda_leftfinger",
                              "panda_rightfinger", "panda_hand_tcp"])
    time.sleep(0.5)   # 給 move_group 一點時間更新內部場景

    # --- 步驟 5：Retreat，直線抬起 ---
    logger.info("[5/6] retreat（Cartesian 直線抬起）")
    grasp_pose = make_grasp_pose(CUBE_POS[0], CUBE_POS[1], CUBE_POS[2] + 0.02)
    traj, frac = cart.straight_line(grasp_pose, (0.0, 0.0, 0.15))
    robot.execute(traj, controllers=[])

    # --- 步驟 6：Place + Detach ---
    logger.info("[6/6] place + detach")
    place = PoseStamped()
    place.header.frame_id = FRAME
    place.pose = make_grasp_pose(PLACE_POS[0], PLACE_POS[1], PLACE_POS[2] + 0.15)
    arm.set_start_state_to_current_state()
    arm.set_goal_state(pose_stamped_msg=place, pose_link="panda_hand_tcp")
    plan_and_execute(robot, arm, logger)

    hand.set_start_state_to_current_state()
    hand.set_goal_state(configuration_name="open")
    plan_and_execute(robot, hand, logger)

    scene.detach("cube", link="panda_hand")
    # detach 之後物件會回到「世界」，但位置是 detach 當下的位置。
    # 如果你要它精準落在 PLACE_POS，記得用 operation=MOVE 更新一次。

    logger.info("完成 ✅")
    rclpy.shutdown()


if __name__ == "__main__":
    main()

🎓 助教筆記：學生今天最會卡的五個問題

1.「我加了物件但 rviz 完全看不到」

症狀：topic pub 成功、沒有錯誤訊息，但 Scene Geometry 是空的。
三個原因，依機率排序：

  • （60%）publisher 太早發。用 rclpy 建完 publisher 立刻 publish，move_group 還沒完成訂閱，訊息掉了。→ 叫學生一律改用 /apply_planning_scene 服務，這條規則能省掉半數的求助。
  • （30%）frame_id 打錯或留空。留空時 TF 找不到參考系，物件被丟棄。診斷：ros2 topic echo /monitored_planning_scene --once | head -60，看 world.collision_objects 是不是空陣列。
  • （10%）rviz 的 MotionPlanning → Scene Geometry → Show Scene Geometry 沒勾。真的常發生，先看這個最快。

2.「Start state in collision，什麼都規劃不出來」

完整錯誤訊息長這樣：[move_group]: Start state appears to be in collision with respect to group panda_arm
診斷指令：

ros2 service call /check_state_validity moveit_msgs/srv/GetStateValidity \
  "{group_name: 'panda_arm'}"
# 直接看 contacts[].contact_body_1 / contact_body_2

四種情況：(a) 夾住東西沒 attach；(b) attach 了但 touch_links 沒填全；(c) 加的桌面 z 太高，把機器人底座包進去了（常見！桌面中心 z 減掉厚度一半才是桌面高度）；(d) 機器人真的處於自碰撞姿態，先 set_goal_state(configuration_name="ready") 回家。

3.「fraction 永遠是 0.0 或 0.1」

優先檢查 link_name 對不對。學生很常填 panda_link8 或 panda_hand，但 SRDF 裡 panda_arm 群組的末端是 panda_hand_tcp。填了不屬於該 group kinematic chain 的 link，服務會回 fraction 0 而不會報錯——這是最惡劣的一種失敗，因為沒有錯誤訊息可查。

# 確認 group 的 tip link 到底叫什麼
ros2 param get /move_group robot_description_semantic | grep -A3 "group name=\"panda_arm\""
# 或直接在 rviz 的 MotionPlanning -> Planning -> 看 End Effector 欄位

其次才是：起始 pose 給錯（用了目標 pose 當起點）、途中有碰撞物件、目標超出工作空間。

4.「MoveItPy 起不來：Parameter 'robot_description' not found」

這是今天最會浪費時間的問題。學生直覺會 python3 pick_place.py，一定失敗。MoveItPy 需要 robot_description、robot_description_semantic、kinematics.yaml、planning pipeline 等一整包參數，這些只能透過 launch 檔的 MoveItConfigsBuilder 注入。

標準解法：複製官方 motion_planning_python_api_tutorial.launch.py，把 Node(package=..., executable=...) 指向自己的檔案。提醒學生：這支 Python 必須是 package 裡的 entry point（setup.py 的 console_scripts），不能是隨便一個 .py。

# 快速確認參數有沒有進去
ros2 param list /pick_place_py | grep robot_description

5.「模擬裡方塊從指縫滑掉／穿過去了」

先講清楚這不是 MoveIt2 的問題。MoveIt2 只管規劃與碰撞模型，Gazebo 管物理。方塊掉下去是摩擦係數（<mu1>/<mu2>）太低、或求解器迭代次數不夠。

教學上的處理方式：告訴學生「rviz 裡方塊跟著手走 = MoveIt2 這邊是對的，作業算過」，Gazebo 的抓取穩定性是另一個題目。真要在模擬裡抓穩，實務做法是用 gazebo_ros_link_attacher 之類的插件在夾爪閉合時建立固定關節——這是公認的作弊但業界普遍在用，Day 19 講 Sim2Real Gap 時會回頭談這件事為什麼會害到實機表現。

📌 給助教的一句話總結
今天所有問題都可以用同一個問句拆開：「這是 MoveIt2 腦中的世界出問題，還是 Gazebo 的物理出問題？」 學生九成的混亂來自把這兩個世界混為一談。先問這句，再決定要看 /monitored_planning_scene 還是看 Gazebo 的 SDF。
