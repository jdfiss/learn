1. 為什麼需要座標轉換：從一個真實情境說起

你的機器人前面裝了一顆雷射雷達。雷達回報：「正前方 1.2 公尺有東西。」

問題來了：

  • 雷達裝在車體前方 20 公分、高 15 公分的地方 → 對車體中心來說，那個東西在前方 1.4 公尺
  • 車體現在朝東北方 45 度、位於地圖上的 (3.0, 2.0) → 對地圖來說，那個東西在 (3.99, 2.99)
  • 你的手臂要去抓它，手臂基座又裝在車體後方 10 公分…

如果每個節點都要自己記住這些偏移量，系統會立刻崩潰：改個安裝位置就要改十個檔案。

tf2 解決的就是這件事：它是一個集中式、帶時間戳的座標關係資料庫。每個節點只負責發佈「我知道的那一段關係」，需要換算時就問 tf2：「請告訴我 A 到 B 的轉換。」

比喻：tf2 像一間公司的組織圖 + 每個人的座位表，而且還有歷史版本。你問「三分鐘前，工程師小王相對於大門在哪」，它會沿著組織圖一路查上去，把每一段的相對位置乘起來給你。

3. 知識點：座標系與剛體變換

3-1　ROS 的座標慣例（REP 103 / REP 105）

先背這兩條，之後每天都用：

機器人本體（右手座標系）：x 向前、y 向左、z 向上。旋轉用 roll（繞 x）、pitch（繞 y）、yaw（繞 z），逆時針為正。

相機／光學（optical frame）：z 向前、x 向右、y 向下。

頭號地雷：相機有兩套 frame——camera_link（機器人慣例）與 camera_depth_optical_frame（光學慣例），兩者差一個 90 度的旋轉組合。Day 18 做視覺抓取時，學生「點雲整個倒過來 / 躺著」的問題，九成是把這兩個 frame 用錯。今天先把這個名字記在腦子裡。

3-2　齊次變換矩陣：把旋轉和平移塞進同一個矩陣

它解決什麼問題：一個剛體變換 = 先轉一下、再移一下。分開寫是 p' = R·p + t，兩個運算。連續做五次變換時，公式會變得很醜、也不好用矩陣連乘化簡。

做法：把三維點多加一個「1」變成四維，就能把旋轉與平移合併成一個 4×4 矩陣的乘法。

┌ ┐ │ r11 r12 r13 tx │ T = │ r21 r22 r23 ty │ ┌ R t ┐ │ r31 r32 r33 tz │ = │ 0 1 │ │ 0 0 0 1 │ └ ┘ └ ┘

每個符號的物理意義：

符號是什麼物理意義
R（左上 3×3）旋轉矩陣子座標系的三根軸（x, y, z）在父座標系裡指向哪個方向。R 的第一行就是子座標系 x 軸在父座標系中的單位向量
t（右上 3×1）平移向量子座標系的原點在父座標系裡的位置，單位公尺
底下那列 0 0 0 1補齊用純粹是為了讓矩陣能相乘、能求逆，沒有物理意義

怎麼用：

一個點在子座標系（例如 laser_link）的座標是 p_child = [x, y, z, 1]ᵀ 換算到父座標系（例如 base_link）： p_parent = T_parent←child · p_child 多段串接（laser → base → odom → map）： T_map←laser = T_map←odom · T_odom←base · T_base←laser 反過來（父換到子）就取逆矩陣： T_child←parent = (T_parent←child)⁻¹

記憶訣竅：把 ← 想成「箭頭指向誰，結果就是誰的座標系」。相鄰的兩個下標會消掉，就像單位換算：(m/cm)·(cm/mm) = m/mm。如果下標消不掉，你就是乘反了——這是檢查自己有沒有搞錯方向最快的方法。

常見誤解：「T_A←B 是把 A 移到 B 的意思」。不是。T_A←B 是把「B 座標系裡的座標」轉換成「A 座標系裡的座標」，同時它也等於「B 座標系本身相對於 A 的位姿」。這兩種讀法是同一件事，但學生常常只記住其中一種就開始亂乘。助教請一律用「下標消去法」教，不要用語言記憶。

3-3　旋轉的三種表示法，以及為什麼 ROS 用 quaternion

表示法幾個數字優點致命缺點
歐拉角 (roll, pitch, yaw)3人看得懂萬向鎖；順序不唯一（xyz? zyx?）；不好插值
旋轉矩陣9直接能算冗餘；數值誤差累積後不再正交
四元數 quaternion4無萬向鎖、好插值、數值穩定人看不懂

萬向鎖是什麼（一定要能白話講）：用歐拉角時，當 pitch 轉到 ±90 度，roll 與 yaw 的旋轉軸會重疊，等於三個自由度掉成兩個，你再怎麼調也轉不到某些姿態。
比喻：像相機三腳架的雲台，當你把鏡頭完全朝正上方時，左右轉盤和底座旋轉會變成同一個動作——你失去了一個方向。

四元數的四個數字：q = (x, y, z, w)（注意 ROS 的順序是 x, y, z, w，很多數學教科書寫 w, x, y, z，複製別人程式碼時要看清楚）

繞單位向量 (ux, uy, uz) 轉 θ 角： x = ux · sin(θ/2) y = uy · sin(θ/2) z = uz · sin(θ/2) w = cos(θ/2) 約束：x² + y² + z² + w² = 1 （必須是單位四元數）
  • (ux, uy, uz)：旋轉軸的方向（單位向量）
  • θ：繞這根軸轉的角度（弧度）
  • w：可以理解成「轉了多少的量」——w = 1 代表完全沒轉（θ=0），w = 0 代表轉了 180 度
  • 那個 θ/2 是四元數的數學結構決定的（它在「一半角度」的空間裡運作），不用深究，但要知道它的存在，否則你會算錯

最常用的特例：只繞 z 軸轉 yaw（地面移動機器人幾乎只用得到這個）

x = 0 y = 0 z = sin(yaw / 2) w = cos(yaw / 2)
常見誤解：「orientation 不填就是不旋轉」。錯。不填是 (0,0,0,0)，模長為 0，是非法四元數，rviz 會警告 Uninitialized quaternion, assuming identity，有些函式會直接算出垃圾。不旋轉要寫 w = 1.0。 這是初學者最常犯、也最容易忽略的錯。

3-4　紙筆練習（請真的動手算，10 分鐘）

雷達裝在車體前方 0.2 m、高 0.15 m，無旋轉。車體位於 odom 的 (3.0, 2.0)，朝向 yaw = 45°。
雷達在自己的座標系裡看到一個點 (1.2, 0.0, 0.0)。

問：這個點在 odom 座標系的位置？

解：
① 先轉到 base_link：(1.2 + 0.2, 0 + 0, 0 + 0.15) = (1.4, 0, 0.15)
② 再轉到 odom（旋轉 45° 再平移）：
　x = 3.0 + 1.4·cos45° − 0·sin45° = 3.0 + 0.99 = 3.99
　y = 2.0 + 1.4·sin45° + 0·cos45° = 2.0 + 0.99 = 2.99
　z = 0 + 0.15 = 0.15
答：(3.99, 2.99, 0.15)

等一下用 tf2_echo 驗算這個答案——親手算過一次，你才會真的相信 tf2 在做什麼。

4. 知識點：map / odom / base_link 三層架構（REP 105）

4-1　為什麼要三層，不能只用一層

這是整個 ROS 導航的核心設計，Day 10 的 Nav2 完全建立在這個結構上。

map
 │  ← 由定位演算法發佈（AMCL / slam_toolbox），會「跳」
 │     修正累積誤差，低頻（1~10 Hz）
odom
 │  ← 由里程計發佈（輪速編碼器 / IMU 融合），平滑但會「飄」
 │     高頻（20~100 Hz）
base_link
 │  ← 由 URDF + robot_state_publisher 發佈，固定不動
 ├── laser_link
 ├── camera_link
 └── imu_link
frame意義性質誰發佈
map世界座標，固定不動不連續（會跳）、長期無漂移AMCL / SLAM
odom開機時的起點連續平滑、長期會漂里程計 / EKF
base_link機器人本體中心——
各感測器 frame感測器安裝位置相對本體固定robot_state_publisher

4-2　關鍵的一句話：為什麼不是 map → base_link 直接一條

因為兩種需求互相衝突：

  • 局部控制（避障、走直線）需要連續平滑的位置——位置突然跳一下，控制器會瘋掉
  • 長期導航需要沒有累積誤差的位置——輪子打滑一小時後，里程計可能差了好幾公尺

魚與熊掌不可兼得，所以 ROS 的解法是拆成兩段：odom → base_link 給你平滑，map → odom 這段由定位演算法即時修正、承擔所有的「跳」。

比喻：odom → base_link 是你自己「閉著眼睛數步伐」推算的位置——很平順，但走久了一定偏。map → odom 是你偶爾睜開眼睛看路標後，對自己整套推算的修正量。你不會因為睜眼修正就讓自己的腳步變得不連續，你是修正「我以為的起點在哪」。

常見誤解：「AMCL 發佈機器人在地圖上的位置」。嚴格說不是——AMCL 發佈的是 map → odom 這段修正量。機器人在地圖上的位置是 map→odom 再串上 odom→base_link 算出來的。這個區別在 Day 11 除錯時非常重要。

4-3　tf 的鐵律：一個 child 只能有一個 parent

tf 是一棵樹，不是圖。
① 每個 frame 只能有一個 parent
② 同一段轉換只能有一個發佈者
③ 樹必須連通，否則查詢會失敗

違反 ① 或 ② 會出現 TF_REPEATED_DATA 或 tf 樹閃爍（兩個發佈者互相覆蓋），這種錯誤不會讓程式崩潰，只會讓機器人行為詭異，是最難抓的一類。

5-2　動態 broadcaster：odom_publisher.py

#!/usr/bin/env python3
"""假里程計：讓 base_link 在 odom 座標系裡繞圈，並正確填 quaternion。"""
import math

import rclpy
from rclpy.node import Node
from geometry_msgs.msg import TransformStamped
from tf2_ros import TransformBroadcaster


class OdomPublisher(Node):
    def __init__(self):
        super().__init__('odom_publisher')
        self.declare_parameter('radius', 1.0)
        self.declare_parameter('omega', 0.4)       # rad/s
        self.declare_parameter('rate', 30.0)       # Hz，tf 建議 20 Hz 以上

        self.r = float(self.get_parameter('radius').value)
        self.w = float(self.get_parameter('omega').value)
        rate = float(self.get_parameter('rate').value)

        self.br = TransformBroadcaster(self)       # 動態用 TransformBroadcaster
        self.t = 0.0
        self.dt = 1.0 / rate
        self.create_timer(self.dt, self.tick)
        self.get_logger().info(f'odom_publisher 啟動 @ {rate} Hz')

    def tick(self):
        self.t += self.dt
        yaw = self.w * self.t

        tf = TransformStamped()
        # ---- 三個一定要填對的欄位 ----
        tf.header.stamp = self.get_clock().now().to_msg()   # 時間戳
        tf.header.frame_id = 'odom'                          # parent
        tf.child_frame_id = 'base_link'                      # child

        tf.transform.translation.x = self.r * math.cos(yaw)
        tf.transform.translation.y = self.r * math.sin(yaw)
        tf.transform.translation.z = 0.0

        # 只繞 z 軸轉 yaw：x=y=0，z=sin(yaw/2)，w=cos(yaw/2)
        tf.transform.rotation.x = 0.0
        tf.transform.rotation.y = 0.0
        tf.transform.rotation.z = math.sin(yaw / 2.0)
        tf.transform.rotation.w = math.cos(yaw / 2.0)

        self.br.sendTransform(tf)


def main():
    rclpy.init()
    node = OdomPublisher()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()


if __name__ == '__main__':
    main()

5-3　靜態 broadcaster：sensor_tf.py

#!/usr/bin/env python3
"""靜態轉換：感測器安裝位置。用 StaticTransformBroadcaster，只需發一次。"""
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import TransformStamped
from tf2_ros import StaticTransformBroadcaster


class SensorTF(Node):
    def __init__(self):
        super().__init__('sensor_tf')
        # 靜態專用：內部用 TRANSIENT_LOCAL QoS，之後才連上的節點也收得到
        self.br = StaticTransformBroadcaster(self)

        tf = TransformStamped()
        tf.header.stamp = self.get_clock().now().to_msg()
        tf.header.frame_id = 'base_link'
        tf.child_frame_id = 'laser_link'
        tf.transform.translation.x = 0.2
        tf.transform.translation.y = 0.0
        tf.transform.translation.z = 0.15
        tf.transform.rotation.w = 1.0      # 不旋轉，w 一定要是 1

        self.br.sendTransform(tf)          # 只送一次就好
        self.get_logger().info('static tf base_link -> laser_link 已發佈')


def main():
    rclpy.init()
    node = SensorTF()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()


if __name__ == '__main__':
    main()
static 與 dynamic 的差別，一定要講清楚：
靜態轉換發到 /tf_static，用 TRANSIENT_LOCAL QoS（有「歷史保留」，晚加入的訂閱者也能收到最後一筆），所以只要發一次。
動態轉換發到 /tf，是一般的 volatile QoS，必須持續發，停了就過期。
學生若用 TransformBroadcaster 只發一次靜態轉換 → 一開始有、幾秒後全部 extrapolation error。

5-4　Listener：把點從一個 frame 換到另一個

#!/usr/bin/env python3
"""查詢 tf 並轉換一個點：驗算上午紙筆的答案。"""
import rclpy
from rclpy.node import Node
from rclpy.duration import Duration

from geometry_msgs.msg import PointStamped
import tf2_ros
# 這行 import 看起來沒用到，但「必須」有：
# 它會註冊 PointStamped 的轉換函式，否則 do_transform_point 找不到型別
from tf2_geometry_msgs import do_transform_point


class PointTransformer(Node):
    def __init__(self):
        super().__init__('point_transformer')

        # Buffer 是那個「資料庫」，Listener 負責訂閱 /tf 與 /tf_static 塞進去
        self.buffer = tf2_ros.Buffer(cache_time=Duration(seconds=10.0))
        self.listener = tf2_ros.TransformListener(self.buffer, self)

        self.create_timer(1.0, self.tick)

    def tick(self):
        # 雷達看到正前方 1.2 公尺有東西
        p = PointStamped()
        p.header.frame_id = 'laser_link'
        p.header.stamp = self.get_clock().now().to_msg()
        p.point.x = 1.2
        p.point.y = 0.0
        p.point.z = 0.0

        try:
            # 方法一：先拿轉換再套用（看得到中間過程，適合教學）
            tr = self.buffer.lookup_transform(
                'odom',                     # target：我要換到哪個 frame
                'laser_link',               # source：資料現在在哪個 frame
                rclpy.time.Time(),          # Time() = 「最新可用的」，最安全
                timeout=Duration(seconds=0.5))
            out = do_transform_point(p, tr)

            self.get_logger().info(
                f'laser(1.2,0,0) -> odom '
                f'({out.point.x:.3f}, {out.point.y:.3f}, {out.point.z:.3f})')

        except tf2_ros.LookupException as e:
            self.get_logger().warn(f'找不到 frame（樹不連通）：{e}')
        except tf2_ros.ExtrapolationException as e:
            self.get_logger().warn(f'時間對不上（外推錯誤）：{e}')
        except tf2_ros.ConnectivityException as e:
            self.get_logger().warn(f'兩個 frame 不在同一棵樹：{e}')
        except tf2_ros.TransformException as e:
            self.get_logger().warn(f'其他 tf 錯誤：{e}')


def main():
    rclpy.init()
    node = PointTransformer()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()


if __name__ == '__main__':
    main()
兩個一定要教學生的細節：
① from tf2_geometry_msgs import ... 這行看起來多餘，但沒有它會噴 TypeError: Invalid type for do_transform_point——因為型別轉換函式是靠 import 副作用註冊的。
② lookup_transform 的時間參數用 rclpy.time.Time()（代表「最新可用」）最安全；用 msg.header.stamp 比較嚴謹但容易外推失敗。教學時先用前者讓學生跑起來，再解釋後者為什麼比較正確。

死法一：時間對不上（Extrapolation）

Lookup would require extrapolation into the future. Requested time 1754812345.678 but the latest data is at time 1754812345.612, when looking up transform from frame [laser_link] to frame [odom]
或 ...extrapolation into the past...

白話：你問「這一刻的轉換」，但 tf 手上最新的資料比你問的時間還舊（或太舊）。tf2 拒絕外推——它寧可報錯，也不猜。

怎麼製造：把 odom_publisher 的 rate 從 30 改成 1，然後在 listener 用 msg.header.stamp 查詢。

診斷：ros2 topic hz /tf（頻率太低？）、ros2 param get /節點 use_sim_time（時間來源不一致？）

四種解法，依情況選：
① 查詢時用 rclpy.time.Time() 拿最新的（最快，但語意上不嚴謹）
② lookup_transform(..., timeout=Duration(seconds=0.1)) 讓它等一下
③ 提高 broadcaster 頻率（tf 建議 ≥ 20 Hz）
④ 用 Buffer(cache_time=Duration(seconds=10)) 加大快取（處理「過去太久」的情況）

死法二：樹不連通 / 多重 parent

錯誤訊息 A："laser_link" passed to lookupTransform argument source_frame does not exist
→ 根本沒有人發佈過這個 frame。可能是拼字錯（laser_link vs lazer_link），或 broadcaster 沒啟動。

錯誤訊息 B：Could not find a connection between 'map' and 'laser_link' because they are not part of the same tree. Tf has two or more unconnected trees.
→ 中間斷了一段。最常見是忘了發 map → odom（還沒跑 AMCL/SLAM）。

錯誤訊息 C：TF_REPEATED_DATA ignoring data with redundant timestamp 或 rviz 裡座標軸瘋狂閃爍
→ 同一段有兩個發佈者在搶。典型情境：你自己寫了一個 static publisher，URDF 的 robot_state_publisher 也在發同一段。

萬用診斷：ros2 run tf2_tools view_frames → 打開 frames.pdf，斷在哪一眼就看到。這是整個 ROS 最值得學生記住的一個指令。

死法三：時間來源不一致（use_sim_time）

錯誤訊息：TF_OLD_DATA ignoring data from the past，或時間戳在 1970 年附近，或所有查詢都 extrapolation。

原因：跑模擬（Gazebo / Isaac Sim）時，時間來自 /clock 這個 topic，而不是系統時鐘。只要有任何一個節點沒設 use_sim_time:=true，它就用系統時間，兩邊差了幾十年。

診斷： 

ros2 param get /節點名 use_sim_time      # 逐一檢查，一個都不能漏
ros2 topic echo /clock --once           # 模擬時間有在跑嗎
ros2 topic echo /tf --once              # 看 stamp 的秒數，是不是接近 0
解法：launch 檔裡用 /**: ros__parameters: use_sim_time: true 一次套用到所有節點，別一個一個設。

Day 8 開始跑 Gazebo，這個坑一定會遇到，今天先認識它。

診斷 SOP（把這段抄進你的助教手冊）

學生說「tf 有問題」時，照這個順序問：
  1. ros2 run tf2_tools view_frames → 樹長什麼樣？連通嗎？
  2. ros2 topic hz /tf → 有在發嗎？頻率夠嗎（≥20 Hz）？
  3. ros2 topic echo /tf_static --once → 靜態的那段在不在？
  4. ros2 run tf2_ros tf2_echo A B → 具體哪兩個 frame 之間出問題？
  5. ros2 param get /節點 use_sim_time → 全部節點一致嗎？
  6. rviz2 加 TF 顯示 → 座標軸有沒有在閃（多重發佈者）？方向對嗎？

9. 🎓 助教筆記：Day 5 學生最會卡的地方

卡點 1：「我看不懂矩陣，是不是學不了機器人」

這是情緒問題不是技術問題，處理方式不一樣。

話術：「你不需要會手算 4×4 矩陣。你需要會的是：知道方向有沒有搞反、知道 tf 報錯時要查什麼。矩陣乘法 tf2 會幫你做。」
然後直接教他「下標消去法」——T_map←odom · T_odom←base，中間的 odom 消掉，剩下 T_map←base，對了。這一招不用懂線性代數也能檢查自己有沒有乘反，學生通常聽完就安心了。

卡點 2：do_transform_point 報型別錯誤

錯誤訊息：TypeError: Invalid type for do_transform_point 或 KeyError: <class 'geometry_msgs.msg._point_stamped.PointStamped'>

原因：忘了 import tf2_geometry_msgs（或該套件沒裝）。轉換函式是靠 import 的副作用註冊到一張表裡的。

解法：sudo apt install ros-humble-tf2-geometry-msgs，並在檔案頂端 import。提醒學生：這個 import 即使 linter 說「未使用」也不能刪。

卡點 3：rviz 顯示 TF 但方向明顯不對（車頭朝側面 / 東西是反的）

三個原因排序：
① 角度單位用了「度」而不是弧度（static_transform_publisher 的 yaw 吃弧度，90 度要寫 1.5708）
② quaternion 沒填 w=1.0 → 非法四元數
③ parent / child 寫反了（--frame-id 是 parent，--child-frame-id 是 child，順序寫反整個樹會倒過來）

診斷：ros2 run tf2_ros tf2_echo A B 會直接印出 Euler angle，跟你預期的比對，比在 rviz 裡瞇眼看快得多。

卡點 4：靜態轉換一開始有、後來就消失

原因：用了 TransformBroadcaster（動態）而不是 StaticTransformBroadcaster，而且只送一次。動態轉換發到 /tf，是會過期的。

診斷：ros2 topic echo /tf_static --once —— 如果空的，就是發錯 topic 了。

順帶一提：這也是為什麼晚啟動的 rviz2 仍然收得到靜態轉換——/tf_static 用 TRANSIENT_LOCAL QoS，會把最後一筆留給新訂閱者。這是 Day 2 QoS 概念的第一個實際應用，可以拿來當例子講。

卡點 5：明明有發 tf，rviz 卻說 No transform from [X] to [odom]

依序檢查：
① rviz 的 Fixed Frame 打錯字（預設是 map，但你根本沒有 map）
② 資料訊息的 header.frame_id 是空字串 → ros2 topic echo 你的topic --once 直接看
③ 訊息的 frame_id 有前導斜線（/laser_link）——ROS2 不接受，必須是 laser_link。這是從 ROS1 移植過來的程式最常見的錯。
④ rviz 比 broadcaster 早啟動，且是靜態轉換發錯 topic（見卡點 4）

卡點 6：「為什麼要有 odom？直接用 map 不行嗎」

這是好問題，代表學生在思考。標準回答（背起來）：

「因為定位會跳，控制不能跳。你的避障控制器如果發現自己突然瞬移了 30 公分，會急打方向盤。所以 ROS 把『平滑但會漂的位置』和『準確但會跳的修正』分成兩段，讓控制器只看平滑的那段（odom→base_link），讓導航看完整的那條。」

再補一句實務觀察：「你之後在 Nav2 會看到，local costmap 的 global frame 用 odom，global costmap 用 map——就是這個道理的直接體現。」（Day 10 會驗證這件事）
