📚 知識點逐個講解

1. 為什麼要學動力學？——位置控制與力矩控制的分水嶺

它解決什麼問題：Day 12 的 IK 只回答「關節要轉到幾度」，完全沒回答「要出多少力才轉得過去」。你叫 IK 算出目標角度，然後直接命令馬達「去那裡」，這叫位置控制——馬達內部的驅動器會自己想辦法。這在手臂輕、動作慢的時候夠用；但當手臂要快速揮動、要抓起 2kg 的東西、或要跟人接觸而不能把人撞傷時，位置控制就不夠了。你必須直接算「力矩」。

白話 + 比喻：位置控制像用 GPS 導航叫車「開到台北車站」，車子怎麼踩油門你不管。力矩控制像你自己開車，每一刻都要決定油門踩幾分——上坡要多踩（重力項）、轉彎要修方向（科氏力）、車子重要提早煞（慣量）。動力學方程就是「這台車在這個姿勢下，各種力各佔多少」的帳本。

對助教的意義：Physical AI 課程後半的 Imitation Learning、Sim2Real 幾乎都在力矩／速度層面出手，學生問「為什麼我的 policy 在模擬跑得好、上實機就抖」，答案八成落在今天這幾個名詞裡。

學生常見誤解：「有 IK 就會控制手臂了。」IK 只是幾何解，它不知道重力存在。實機上你把 IK 解丟給一支沒有重力補償的手臂，它會往下垂並在目標點附近抖——因為控制器一直在跟重力打架。

2. 動力學方程：M(q)q̈ + C(q,q̇)q̇ + G(q) + F(q̇) = τ

它解決什麼問題：這一條式子把「關節要出多少力矩」和「手臂會怎麼動」綁在一起。給 τ 算 q̈ 叫正向動力學（模擬器在做的事：Gazebo / Isaac Sim 每個 timestep 都在解這個）；給想要的 q̈ 算 τ 叫逆向動力學（控制器在做的事）。

M(q)·q̈ + C(q,q̇)·q̇ + G(q) + F(q̇) = τ
符號叫什麼物理意義（白話）會怎麼咬你
q, q̇, q̈關節角度／角速度／角加速度n 個關節就是 n 維向量。手臂的「狀態」。單位一定是 rad 與 rad/s，不是度。學生最常錯這裡。
M(q)慣量矩陣（Mass / Inertia Matrix）「這個姿勢下手臂有多難推動」。n×n 矩陣，會隨姿勢改變——手臂伸直時對基座來說很重，收起來時很輕（花式滑冰選手收手加速轉）。對角線是各關節自己的慣量，非對角線是「轉 joint2 會連帶推動 joint1」的耦合。它不是常數。學生把它當常數調一組 PID gains，在某個姿勢好、換姿勢就爛。
C(q,q̇)·q̇科氏力與離心力項只在「動起來」才存在，且跟速度平方成正比。離心力＝旋轉時把東西往外甩；科氏力＝一邊轉一邊伸長手臂時產生的側向力（像在旋轉木馬上往外走，你會被推向側面）。慢速動作時可以忽略，這是為什麼很多教學程式不算它也能動。速度一快就爆掉。
G(q)重力項「手臂靜止在這個姿勢，光是不掉下來要多少力矩」。只跟姿勢有關，跟速度無關。是所有項裡最大也最好處理的一個。沒補這一項＝手臂會垂、會有穩態誤差。這是實機第一天最常見的現象。
F(q̇)摩擦項黏滯摩擦（跟速度成正比）＋庫倫摩擦（跟方向有關的固定值）。減速機、皮帶都在這裡。模擬器裡通常設得太小或沒設 → Sim2Real gap 的頭號來源（Day 19 會回來算帳）。
τ關節力矩馬達真正輸出的東西，單位 N·m。旋轉關節是力矩、線性關節（滑軌）是力 N。每顆馬達有 τ_max。IK 算得出來≠馬達出得起這個力矩。
抓重點：四項的量級大小順序在一般手臂上是 G(q) ≫ M(q)q̈ > F(q̇) > C(q,q̇)q̇（低速時）。所以「只補重力」就能拿到八成效果——這是今天最實用的一句話。

3. PID 控制：誤差回饋的三種吃法

它解決什麼問題：你不可能完美知道 M、C、G（模型永遠有誤差），所以需要一個「不管為什麼錯了，錯了就修」的機制。PID 就是最便宜有效的那個。

τ = Kp·e + Ki·∫e dt + Kd·ė　，其中 e = qdesired − qactual
  • Kp（比例，現在）：差多少就出多少力，像彈簧——拉得越開回彈越強。太小→到不了目標（穩態誤差）；太大→過衝、震盪。
  • Ki（積分，過去）：把「一直差一點」的歷史累積起來，專門消滅穩態誤差。像一個記仇的人：你欠我一點點很久了，我終究要討回來。副作用是反應變慢、容易震盪。
  • Kd（微分，未來）：看誤差變化的速度，像阻尼器／避震器——快接近目標時先煞車，抑制過衝。對雜訊極度敏感（微分把雜訊放大）。

調參順序（給學生的口訣）：先只開 P 調到「會動、稍微過衝」→ 加 D 把過衝壓掉 → 最後才小量加 I 消掉殘留誤差。先 P、後 D、最後 I。

學生常見誤解一：「Kp 越大越精準。」不對。Kp 太大會讓系統進入震盪甚至發散，而且會放大感測器雜訊變成馬達尖叫。
學生常見誤解二：「積分項一定要加。」在有重力補償的手臂上，I 項常常是抖動來源。而且會遇到 integral windup（積分飽和）：馬達已經出到最大力矩了但還沒到位，積分項繼續無腦累加，等到終於動起來會嚴重過衝。解法是 i_clamp（積分項上限）——ros2_control 的 PID 參數裡就有這一項，這也是學生第一次看 YAML 時最不懂的欄位。

4. 重力補償（Gravity Compensation）：投報率最高的一招

它解決什麼問題：純 PID 要靠「先產生誤差」才會出力，所以手臂必然先垂一點才會被拉回來。重力補償是「不等它垂，我先把撐住的力矩喂進去」。

τ = G(q) + Kp·e + Kd·ė

白話 + 比喻：像扶著一個學走路的小孩。純 PID 是「等他快跌倒才拉」；重力補償是「一直輕輕托著他的重量，PID 只負責修方向」。因為 G(q) 只跟姿勢有關，你隨時算得出來，不需要知道速度或加速度——所以它便宜、穩定、幾乎沒有副作用。

一個立刻能懂的實驗：協作機器人（UR、Franka）可以用手直接推著它走，鬆手就停在那——那就是純重力補償模式，控制器只出「撐住自己」的力矩，其餘交給你的手。

學生常見誤解：「重力補償要知道手臂在哪。」它需要的是目前的關節角度（用來算 G(q)），不是目標角度。學生常誤用 q_desired 去算 G，在快速運動時就會補錯方向。

5. 計算力矩控制（Computed Torque / Inverse Dynamics Control）

它解決什麼問題：重力補償解決了靜態，但快速運動時 M(q)q̈ 和 C 也不小。計算力矩控制把整條動力學方程都拿來當「前饋（feedforward）」，讓剩下要靠回饋修的誤差趨近於零。

τ = M(q)·[ q̈d + Kd·ė + Kp·e ] + C(q,q̇)·q̇ + G(q)

每一塊在幹什麼：

  • q̈d：想要的加速度（來自軌跡規劃，MoveIt2 的 trajectory 就帶著這個）——這是前饋，不用等誤差發生。
  • Kdė + Kpe：修模型不準的殘差。
  • 乘上 M(q) 再加 C + G：把「我想要的加速度」翻譯成「馬達要出的力矩」。

為什麼這招很漂亮（feedback linearization）：如果模型 100% 準，把上式代回動力學方程，M、C、G 全部消掉，剩下 ë + Kdė + Kpe = 0——一條乾淨的二階線性微分方程。意思是：不管手臂多重、多複雜、在什麼姿勢，誤差都以你指定的方式收斂。你可以直接用 Kp=ω², Kd=2ζω 設計你要的響應（ζ=1 臨界阻尼，不過衝）。

比喻：重力補償是「托住體重」；計算力矩是「連他下一步要往哪跨、跨多快都預先幫他配好力」。前者只看姿勢，後者連未來的加速度都算進去。

學生常見誤解：「計算力矩比 PID 好，所以永遠用它。」它完全依賴模型精度。連桿質量、質心位置、慣量張量寫錯（URDF 的 <inertial> 是學生最愛亂填的地方，常見「隨便填 1」），計算力矩會比純 PID 更糟——因為它自信地把錯的前饋大力灌進去。實務上：模型不確定就用 PD+重力補償；模型好且要求高速精準才上計算力矩。

6. 阻抗控制與導納控制：跟世界接觸時要「軟」

它解決什麼問題：前面全部是「位置追蹤」思維——目標在哪就去哪，撞到東西也要去。這在插孔、擦桌子、跟人協作時會出事：位置差一點點，剛性控制器就會用巨大力矩硬幹，把工件／手指／自己弄壞。

F = Kx·(xd − x) + Dx·(ẋd − ẋ) + Mx·(ẍd − ẍ)
  • Kx（剛度 stiffness，N/m）：偏離目標 1 公尺要出多少力。設大＝硬，設小＝軟。
  • Dx（阻尼 damping）：吸震，避免碰到東西後彈跳震盪。
  • Mx（虛擬質量）：讓末端「感覺起來」有多重。通常設小或忽略。
  • 注意這裡的 x 是末端在笛卡兒空間的位置，不是關節角度。要靠 Day 12 的 Jacobian 轉換：τ = Jᵀ·F。這就是為什麼 Day 12 必須先學 Jacobian。

白話 + 比喻：阻抗控制＝「在末端和目標點之間掛一根虛擬彈簧＋避震器」，你可以自由指定這根彈簧多硬。硬得像鐵棒＝傳統位置控制；軟得像橡皮筋＝可以被人推開、插孔時會自己滑進去。

阻抗 vs 導納（一句話分清）：阻抗控制＝量位置偏差、輸出力矩（不需要力感測器，靠關節力矩控制實現，Franka / 協作機器人的做法）。導納控制＝量力、輸出位置命令（需要力／力矩感測器，外層包在既有位置控制器外面，工業手臂加 F/T sensor 的做法）。兩者是彼此的「因果反過來」。

學生常見誤解：「阻抗控制 ＝ 力控制。」不是。純力控制是「不管你在哪，我就出 5N」；阻抗控制是「力隨偏差而定」，它同時管位置和力，用剛度參數在兩者之間滑動。而且——只有力矩控制介面的手臂才能做阻抗控制。學生常想在只有位置介面的便宜伺服馬達（例如 SO-100 的 STS3215）上做阻抗控制，硬體上就不可能（只能做很粗糙的導納近似）。

7. ros2_control：把上面這些放進 ROS2 的地方

它解決什麼問題：你不會想為每一台機器人重寫一次控制迴圈。ros2_control 是一個標準框架：硬體怎麼接（hardware interface）和怎麼控（controller）分開，換機器人只換前者，換控制策略只換後者。MoveIt2 規劃出來的軌跡，最後就是交給 ros2_control 的 controller 去執行。

四個必須記住的角色

角色做什麼比喻
controller_manager唯一的主程式（那個 real-time loop）。負責載入／啟動／停止 controller，並在每個週期呼叫 read() → update() → write()。工廠廠長，敲鐘決定每個節拍誰做事。
hardware_interface你為自己機器人寫的插件。宣告「我提供哪些 state_interface（能讀：position/velocity/effort）和哪些 command_interface（能寫：position/velocity/effort）」。在 URDF 的 <ros2_control> 區塊裡宣告。翻譯官，把 USB/CAN/EtherCAT 講成 ROS 聽得懂的話。
resource_manager管理誰佔用哪個 interface。兩個 controller 不能同時寫同一個關節的 position。會議室訂位系統，不准重複預約。
各種 controllerjoint_state_broadcaster（把狀態發成 /joint_states，幾乎所有機器人都要開這個）、joint_trajectory_controller（MoveIt2 用的主力）、forward_command_controller／effort_controllers（直接灌值，測試用）、diff_drive_controller（Day 8–11 的 TurtleBot3 就是這個）。各科師傅，共用同一套廠房。
今天最重要的心智連結：「hardware 提供 effort command interface」→ 你才可能做重力補償／阻抗控制。「只提供 position command interface」→ 你只能做位置控制，動力學那些招全部用不上。看一台機器人能不能做 Physical AI 的力控研究，第一件事就是查它的 command interface 有沒有 effort。
學生常見誤解：「ros2_control 是 controller，MoveIt2 是另一個 controller，兩者衝突。」不是。MoveIt2 是規劃器，它只產生軌跡然後透過 FollowJointTrajectory action 交給 ros2_control 的 joint_trajectory_controller 執行。兩者是上下游，不是競爭關係。

B. 核心實作：單連桿手臂，三種控制器同場比較

這是今天最重要的 30 分鐘。不用 ROS、不用模擬器，純 Python 就能親眼看到「重力補償」和「計算力矩」到底差在哪。存成 day13_control_compare.py 直接跑。

#!/usr/bin/env python3
"""
Day 13: 單連桿手臂（一根均勻桿子繞一端旋轉）三種控制器比較
動力學： I*theta_dd + b*theta_d + m*g*(l/2)*cos(theta) = tau
  - I = m*l^2/3     繞端點的轉動慣量（均勻桿）
  - b*theta_d       黏滯摩擦 F(q_dot)
  - m*g*(l/2)*cos   重力項 G(q)，theta 從水平量起
目標：追蹤一條正弦軌跡，看誰的誤差小
"""
import numpy as np
import matplotlib
matplotlib.use("Agg")          # 無視窗環境也能存圖
import matplotlib.pyplot as plt

# ---------- 真實物理參數（"真實世界"）----------
m, l, g, b = 2.0, 0.6, 9.81, 0.25      # kg, m, m/s^2, N*m*s/rad
I = m * l**2 / 3.0

# ---------- 控制器用的模型（可以故意設成不準，模擬 model error）----------
m_hat, l_hat, b_hat = 2.0, 0.6, 0.25   # 改成 1.6 / 0.55 可看模型誤差的殺傷力
I_hat = m_hat * l_hat**2 / 3.0

def G_true(th):  return m * g * (l / 2.0) * np.cos(th)      # 真實重力力矩
def G_hat(th):   return m_hat * g * (l_hat / 2.0) * np.cos(th)  # 模型估的重力力矩

# ---------- 期望軌跡：從水平開始的正弦擺動 ----------
A, w = 0.6, 2.0                         # 幅值 rad, 角頻率 rad/s
def traj(t):
    return (A * np.sin(w * t),          # theta_d
            A * w * np.cos(w * t),      # theta_d_dot
           -A * w * w * np.sin(w * t))  # theta_d_ddot

# ---------- 模擬主迴圈 ----------
DT, T_END, TAU_MAX = 0.001, 6.0, 40.0   # 1 kHz 控制頻率, 馬達力矩上限 N*m

def simulate(mode, Kp, Kd, Ki=0.0, i_clamp=5.0):
    th, thd, ei = 0.0, 0.0, 0.0
    ts, errs, taus = [], [], []
    for k in range(int(T_END / DT)):
        t = k * DT
        th_d, thd_d, thdd_d = traj(t)
        e, ed = th_d - th, thd_d - thd
        ei = np.clip(ei + e * DT, -i_clamp, i_clamp)   # 積分項要夾住！anti-windup

        if mode == "pid":
            # 什麼都不知道，純靠誤差硬幹
            tau = Kp * e + Kd * ed + Ki * ei
        elif mode == "pd_grav":
            # 先把重力撐住，PD 只修剩下的
            tau = G_hat(th) + Kp * e + Kd * ed
        elif mode == "computed_torque":
            # 連想要的加速度都前饋進去
            tau = I_hat * (thdd_d + Kd * ed + Kp * e) + b_hat * thd + G_hat(th)
        else:
            raise ValueError(mode)

        tau = np.clip(tau, -TAU_MAX, TAU_MAX)          # 馬達出得起的力矩是有限的

        # ---- 正向動力學：算真實世界會怎麼動（Euler 積分）----
        thdd = (tau - b * thd - G_true(th)) / I
        thd += thdd * DT
        th  += thd * DT

        ts.append(t); errs.append(e); taus.append(tau)
    return np.array(ts), np.array(errs), np.array(taus)

# 三者用「同一組」Kp/Kd，才看得出差別來自前饋而不是調參
runs = {
    "PID only        ": simulate("pid",             Kp=120.0, Kd=12.0, Ki=40.0),
    "PD + gravity comp": simulate("pd_grav",        Kp=120.0, Kd=12.0),
    "Computed torque  ": simulate("computed_torque", Kp=400.0, Kd=40.0),
}
# 註：computed torque 的 Kp/Kd 是「誤差方程的係數」而非力矩增益
#     (Kp=w^2=400 -> w=20 rad/s, Kd=2*zeta*w=40 -> zeta=1 臨界阻尼，不過衝)

print(f"{'controller':<18} {'RMS err(rad)':>13} {'max err(rad)':>13} {'max tau(N*m)':>13}")
for name, (ts, e, tau) in runs.items():
    half = len(e) // 2          # 只看後半段（穩態），前半段是啟動暫態
    print(f"{name:<18} {np.sqrt(np.mean(e[half:]**2)):>13.5f} "
          f"{np.max(np.abs(e[half:])):>13.5f} {np.max(np.abs(tau)):>13.2f}")

fig, ax = plt.subplots(2, 1, figsize=(9, 7), sharex=True)
for name, (ts, e, tau) in runs.items():
    ax[0].plot(ts, e, label=name.strip())
    ax[1].plot(ts, tau, label=name.strip())
ax[0].set_ylabel("tracking error (rad)"); ax[0].legend(); ax[0].grid(alpha=.3)
ax[0].axhline(0, color="k", lw=.8)
ax[1].set_ylabel("torque (N*m)"); ax[1].set_xlabel("time (s)")
ax[1].legend(); ax[1].grid(alpha=.3)
plt.tight_layout(); plt.savefig("day13_compare.png", dpi=110)
print("\n圖已存成 day13_compare.png")
你應該看到的結果：PID 的誤差是一條偏離 0 的波浪（重力一直在拉，積分項追不上變化）；PD+重力補償的誤差明顯縮小且對稱；計算力矩的誤差幾乎貼在 0。
接著做這個實驗（重要）：把 m_hat 改成 1.4（模型比實際輕 30%，模擬你 URDF 的 inertial 填錯），再跑一次。你會看到計算力矩的優勢大幅縮水——這就是上面那個「模型不準時計算力矩會反過來害你」的活教材，也是 Day 19 Sim2Real gap 的預告。

C. 用 Robotics Toolbox 看真實 7 軸手臂的 M(q) 和 G(q)

#!/usr/bin/env python3
"""看一支真實手臂的動力學各項有多大，建立數量級直覺"""
import numpy as np
import roboticstoolbox as rtb

robot = rtb.models.DH.Panda()          # Franka Panda，7 軸
q  = robot.qr                          # 一個 ready 姿勢
qd = np.zeros(7)
qdd = np.zeros(7)

print("=== G(q)：光是撐住自己需要的力矩 (N*m) ===")
print(np.round(robot.gravload(q), 3))

print("\n=== M(q)：慣量矩陣（看對角線大小與非對角的耦合）===")
np.set_printoptions(precision=3, suppress=True)
print(robot.inertia(q))

print("\n=== 同一支手臂，換姿勢後 G(q) 完全不同 ===")
for name, qq in [("qr (ready)", robot.qr), ("qz (全零/伸直)", robot.qz)]:
    print(f"{name:<16} |G| = {np.linalg.norm(robot.gravload(qq)):.3f} N*m")

print("\n=== 逆向動力學 rne()：要達到指定 q,qd,qdd 需要的 tau ===")
qd_fast = np.ones(7) * 1.5             # 每個關節 1.5 rad/s
qdd_fast = np.ones(7) * 2.0
tau_static  = robot.rne(q, np.zeros(7), np.zeros(7))   # 只有重力
tau_dynamic = robot.rne(q, qd_fast, qdd_fast)          # 加上 M 和 C 的貢獻
print("靜止時 tau :", np.round(tau_static, 2))
print("快速時 tau :", np.round(tau_dynamic, 2))
print("差額(M+C的份):", np.round(tau_dynamic - tau_static, 2))

看完你會有一個關鍵直覺：靜止時的力矩幾乎全部是重力，這就是為什麼重力補償投報率最高。

# config/my_arm_controllers.yaml
controller_manager:
  ros__parameters:
    update_rate: 500          # Hz，控制迴圈頻率。力矩控制建議 >= 500，位置控制 100 也行

    joint_state_broadcaster:  # 幾乎所有機器人都要開，否則 /joint_states 是空的、rviz 顯示不出來
      type: joint_state_broadcaster/JointStateBroadcaster

    arm_trajectory_controller: # MoveIt2 的執行端
      type: joint_trajectory_controller/JointTrajectoryController

    arm_effort_controller:     # 力矩直灌，做重力補償實驗時用
      type: effort_controllers/JointGroupEffortController

arm_trajectory_controller:
  ros__parameters:
    joints: [joint1, joint2, joint3, joint4, joint5, joint6]
    command_interfaces: [position]        # 硬體吃什麼就寫什麼
    state_interfaces:  [position, velocity]
    allow_partial_joints_goal: false
    open_loop_control: false

    # 容忍度：超過就會回報 GOAL_TOLERANCE_VIOLATED / PATH_TOLERANCE_VIOLATED
    constraints:
      stopped_velocity_tolerance: 0.02
      goal_time: 0.6                     # 允許比軌跡規定時間多花 0.6 秒
      joint1: {trajectory: 0.15, goal: 0.05}   # 過程容忍 / 終點容忍（rad）
      joint2: {trajectory: 0.15, goal: 0.05}

    # 若 command_interface 是 effort，這裡才需要 PID
    gains:
      joint1: {p: 120.0, i: 1.0, d: 12.0, i_clamp: 5.0, ff_velocity_scale: 0.0}
      joint2: {p: 120.0, i: 1.0, d: 12.0, i_clamp: 5.0, ff_velocity_scale: 0.0}
      # i_clamp 就是上面講的 anti-windup 上限，別留 0（等於關掉 I）也別留超大值

arm_effort_controller:
  ros__parameters:
    joints: [joint1, joint2, joint3, joint4, joint5, joint6]
    interface_name: effort

🎓 助教筆記：今天這個主題，學生一定會來問的 6 件事

坑 1｜「Could not contact service /controller_manager/list_controllers」

症狀：執行 ros2 control list_controllers 直接報這一行，或 spawner 卡住 timeout。
真正原因（依機率排序）：(1) controller_manager 根本沒起來（launch 檔錯誤，去看終端最上面的紅字）；(2) controller_manager 起在別的 namespace，要用 -c /my_ns/controller_manager；(3) ROS_DOMAIN_ID 兩個終端不一樣（Day 24 會再遇到一次）。
診斷指令：

ros2 node list | grep controller_manager     # 節點在不在
ros2 service list | grep controller_manager  # service 有沒有起
echo $ROS_DOMAIN_ID                          # 兩個終端要一樣
ros2 control list_controllers -c /控制器命名空間/controller_manager

坑 2｜手臂在 Gazebo 裡直接垂下去 / 瘋狂抖動

症狀：模擬一開就整支手臂軟趴趴掉到地上，或高頻震動到爆炸。
原因：垂下去＝沒有任何 controller 在 active（list_controllers 會顯示 inactive 或空的），或 command_interface 是 effort 但 gains 全為 0；抖動＝Kp 太大、或 update_rate 太低（力矩控制用 100 Hz 一定抖）、或 URDF 的 <inertial> 質量／慣量填得不合物理（例如 mass=0.001 但 inertia=1.0）。
診斷順序：先 ros2 control list_controllers 看有沒有 active → 看 YAML 的 update_rate → 用 check_urdf 和目視檢查每個 link 的 inertial → 把 Kp 砍半看抖動是否減輕（會減輕就是 gains 問題）。

坑 3｜「Trajectory message contains waypoints that are not strictly increasing in time」

症狀：送軌跡給 joint_trajectory_controller 被直接拒絕。
原因：學生自己手刻 JointTrajectory 訊息時，time_from_start 兩個點相同（常見：都填 0，或都填 1.0），或第一個點就填 0。
解法：time_from_start 必須嚴格遞增且第一點 > 0。這是學生手寫軌跡時 100% 會踩的一坑，Day 16 用 MoveIt2 就不會遇到（規劃器會幫你算），所以要提醒他們「手刻軌跡只用於測試」。

坑 4｜「Joint 'xxx' not found in hardware interfaces」/ controller 載入失敗

症狀：controller 一直停在 unconfigured，log 說找不到某個 interface。
原因：三處 joint 名稱不一致（URDF / <ros2_control> / YAML），或 YAML 寫 command_interfaces: [effort] 但 URDF 裡只宣告了 position。
診斷指令：

# 看硬體「實際」提供了什麼，這是唯一的事實來源
ros2 control list_hardware_interfaces
# 輸出範例，注意 [available] / [claimed] 標記：
#   command interfaces
#         joint1/position [available] [claimed]
#         joint1/effort   [available] [unclaimed]   <- YAML 想要 effort 就要看到這行
# 檢查 xacro 展開後的 URDF 到底長什麼樣（學生常改了 xacro 卻沒重 build）
xacro src/my_robot/urdf/robot.urdf.xacro > /tmp/out.urdf && grep -A3 ros2_control /tmp/out.urdf

坑 5｜「調 PID 調到崩潰」/ 學生問「Kp 要設多少？」

怎麼回答：不要給數字，給流程。(1) 先把 I 設 0、D 設 0，Kp 從小往上加到「會動、輕微過衝」；(2) 加 D 壓過衝，D 通常是 Kp 的 1/10 量級起跳；(3) 若仍有固定的殘留誤差，才小量加 I 並務必設 i_clamp；(4) 若手臂在某姿勢好、某姿勢爛，那不是 PID 的問題，是 M(q) 和 G(q) 隨姿勢改變——去做重力補償，不要繼續調 PID。第 (4) 點是今天最值得教給學生的判斷。

坑 6｜「我在 SO-100／便宜伺服上做不了阻抗控制」

症狀：學生看完論文想做 compliant control，發現硬體不給力矩介面。
怎麼回答：誠實講硬體限制：STS3215 這類 smart servo 只給位置（頂多電流讀值），做不了真正的關節力矩控制。折衷方案：(a) 用電流讀值做粗略的碰撞偵測後停止；(b) 降低伺服的 P gain 讓它「軟」一些（機械上的順從）；(c) 想做真力控就要 Franka / UR / 或帶 torque sensor 的手臂。提前講清楚可以省掉學生兩週的白工——這正是 Day 22–23 Imitation Learning 為什麼多用位置層 policy 的硬體原因。
